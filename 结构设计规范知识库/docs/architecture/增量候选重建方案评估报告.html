一、执行摘要

结论先行

结论：历史全量重建不是错误实现，它优先保证了候选版本隔离、质量门禁和回滚能力；但每次新增规范都重新解析和向量化全部规范，随着文档数量增加会造成不必要的时间、费用和运维压力。当前代码已保留全量重建作为兜底路径，并把“增量处理、完整候选发布”设为日常默认路径。

历史基线

每次重建扫描数据源目录中的全部 PDF，重新解析全部文档，重新生成全部 Embedding，并构建新的 Chroma 运行版本。

保留为兜底

当前真实状态

使用 PDF、元数据、校对修订、结构化表修订和处理契约指纹判断文档是否可复用，只处理新增或变化文档，然后在独立候选目录中组装完整版本。

已实现并回归

不可牺牲的能力

候选版本不直接影响在线服务；质量门禁失败不能切换活动指针；活动版本必须可回滚；检索元数据、页面证据和结构化表必须保持一致。

强约束

二、历史基线：全量候选重建

以下内容描述增量方案实施前的基线行为；该路径现在仍作为强制全量和自动回退入口保留。

2.1 基线构建链路

1. 扫描数据源读取 DATA_DIR/raw 下的全部 PDF。
2. 清理产物清理候选版本的数据库、解析文本、图片、MinerU 和审计目录。
3. 解析规范调用 MinerU 或 PyMuPDF，生成元素、Chunk、图片和审计结果。
4. 全量向量化对全部 Chunk 调用智谱 Embedding，删除旧集合并写入新集合。
5. 门禁激活构建候选版本，运行检索检查，通过后原子切换活动指针。

2.2 继续保留的版本隔离机制

管理端重建会将候选版本写入 data/db_versions/{job_id}/，包括数据库、解析文本、图片、MinerU 产物、审计目录、manifest 和质量证据。候选版本通过预激活门禁后，系统更新 data/active_db.json，再让在线检索状态采用候选版本。

环节当前实现结果
源文件发现扫描指定目录中的全部 PDF当前增量和强制全量路径都以该目录为输入
解析基线路径对全部 PDF 执行解析仅在强制全量或安全回退时继续发生
Embedding基线路径对全部 Chunk 重新请求向量仅在向量契约迁移、缓存不可用或强制全量时继续发生
向量库删除候选库中的旧集合，再一次性写入候选内部一致，无法利用旧向量
BM25从候选运行数据重新生成本地成本较低，但仍需完整数据
发布预激活门禁通过后切换活动指针回滚边界清晰，适合保留

相关代码：builder.py、load_to_db.py、重建工作流、候选版本事务化激活 ADR。

三、历史基线的问题评估

3.1 性能与成本

  • 新增一份规范会触发全部规范的解析、Chunk 化和向量化。
  • Embedding 调用数量与总 Chunk 数成正比，文档规模扩大后费用和限流风险都会增加。
  • 复杂表和扫描 PDF 的 MinerU 解析是主要耗时来源，重复处理没有内容收益。
  • 后台任务占用时间变长后，用户更难判断任务是否卡滞，也更容易遇到服务维护窗口。

3.2 数据一致性

直接向在线 Chroma 追加向量虽然速度快，但会破坏当前最重要的版本边界：当解析、Embedding、BM25、图片和 manifest 不是同一批提交时，在线回答可能引用混合版本。当前事务化候选方案正是为避免这种情况建立的，因此不应简单改成“在线库直接追加”。

3.3 当前架构已经具备的可复用基础

文档指纹

manifest 已记录 PDF 的 SHA-256、大小、Chunk 数和 Chunk ID，可以作为文档变更检测的基础。

活动指针

active_db.json 已经将数据库、解析文本、图片、MinerU 和 manifest 绑定到同一个活动版本。

候选门禁

当前可以在候选版本上检查 manifest、Chroma 条目数、解析产物和结构化检索结果。

失败保留旧版本

候选失败时不更新活动指针，这个发布语义应继续保持。

四、当前方案：增量候选重建

核心原则：只增量处理内容，仍然完整生成候选版本；该原则已经落入默认重建路径。

“增量”只代表解析和向量化的输入范围变小，不代表直接修改在线运行状态。最终仍然要形成一份包含全部活动文档的完整候选知识版本，并通过现有发布门禁。

4.1 目标链路

1. 扫描数据源扫描服务器可访问的源目录，计算 PDF 哈希并读取元数据；浏览器上传尚未实现。
2. 变更分类判断新增、未变化、内容变化、元数据变化、删除。
3. 增量处理只解析变化文档，只为变化 Chunk 请求 Embedding。
4. 候选组装复用未变化文档的解析产物、图片和向量缓存。
5. 全局验证激活重新生成检索辅助索引，执行门禁并原子切换。

4.2 已采用的候选组装方式

当前继续使用“单一完整 Chroma 集合”，但在新的候选目录中组装。对未变化文档，从已通过门禁的不可变活动版本读取解析资产，并从活动精确向量索引复用兼容向量；对新增或变化文档，完成解析后仅为未命中的 Chunk 生成新向量。这样避免 Embedding API 重复调用，同时保留完整候选数据库和现有检索接口。

不建议直接复制正在被在线进程使用的 Chroma 数据目录作为增量基础。文件级复制可能遇到 SQLite、HNSW 持久化和缓存状态不一致。更稳妥的方式是使用受控的文档资产和向量缓存重新写入候选集合。

4.3 长期扩展：索引分片

当规范数量达到数百份、单一候选集合重组仍成为瓶颈时，可以把文档或文档组拆成不可变索引分片，由活动 manifest 管理分片集合。查询时并行召回各分片，再统一进行权威性、表格优先和精排合并。分片不是当前第一选择，因为它会增加跨分片召回、删除、排序、统计和证据一致性复杂度。

五、增量方案的数据模型

增量可靠性的关键不是“比较文件名”，而是比较完整的内容与处理契约。

5.1 文档变更指纹

字段用途变化后的处理
source_file文档稳定身份和引用来源同名文件替换时必须继续比较哈希
sha256判断 PDF 内容是否变化变化则重新解析
parser_backend、版本、参数判断解析结果是否可复用解析器契约变化则重新解析
correction_revision判断已审批修正是否变化修正变化则重新生成受影响 Chunk
embedding_model、维度判断向量是否兼容模型或维度变化时执行全量向量迁移
metadata_revision判断规范名称、编号、版本等是否变化可只重建元数据和索引，必要时重新生成 Chunk
chunk_id、文本哈希判断单个 Chunk 是否可复用未变化则复用向量，变化则重新 Embedding

5.2 已采用的资产层

data/
  document_cache/
    index.json                 # 激活成功后原子发布的派生缓存索引
  db_versions/<job-id>/      # 完整候选运行版本
    db/
    processed/
    images/
    mineru/
    audit/
    manifest.json

可信复用源不是一个可变的独立缓存目录，而是已经通过门禁的不可变活动版本及其精确向量索引。document_cache/index.json 只保存可重建的诊断索引，不是活动提交点。向量复用前会核对模型、维度、请求契约和数值有效性，避免把不兼容向量混入候选版本。

六、典型运行流程

6.1 新增规范

  1. 文件进入服务器数据源目录，构建器发现 PDF 并计算 SHA-256。
  2. 读取或创建来源元数据，检查规范编号、名称、版本和来源状态。
  3. 与当前活动 manifest 比较，标记为 added。
  4. 仅调用解析器处理新增 PDF。
  5. 从活动精确向量索引复用稳定 Chunk，只为新增或变化且未命中的 Chunk 调用 Embedding。
  6. 将活动版本中未变化文档的缓存资产和新文档资产组装到候选版本。
  7. 在候选版本上生成 BM25、dense 辅助索引、manifest 和质量报告。
  8. 通过门禁后切换活动指针；失败时保留旧版本和候选诊断材料。

6.2 修改或替换规范

同名文件不能仅按文件名覆盖。系统必须比较 SHA-256。内容变化时，旧文档的所有 Chunk、图片和证据资产从候选版本中移除，再以新结果替换。不能只追加新 Chunk，否则会留下旧内容，造成重复命中和过期答案。

6.3 删除规范

删除操作应先记录为显式变更，再在候选版本组装时排除对应文档。旧活动版本仍保留在版本目录，直到通过版本保留策略清理。不能直接删除活动 Chroma 中的条目后再等待重建完成。

6.4 校对修正和复杂表发布

已审批文本修正、复杂表结构化发布和文档元数据变化都必须参与变更指纹。若修正只影响某个 Chunk，可以只重建该 Chunk；若修正影响页面、表格关系或跨 Chunk 结构，应把整个文档标记为变化，重新生成该文档的完整资产。

七、方案比较与推荐结论

方案重复计算在线一致性回滚实现复杂度结论
强制全量候选重建高高高低保留为兜底和契约迁移路径
在线 Chroma 直接追加低低低中不采用，容易半更新和难回滚
增量资产 + 完整候选集合新增或变化部分高高中高当前默认方案
文档级索引分片新增或变化部分高高高长期规模化备用
只交付预构建知识包由维护者承担高高低适合运行端，不解决维护端新增文档成本
实施结论：已采用“不可变活动资产复用 + 精确向量复用 + 独立候选版本组装 + 现有质量门禁”的增量候选重建。事务化激活、活动指针和失败保留旧版本机制全部保留。

八、风险、门禁与安全边界

向量契约漂移

模型、维度、归一化方式或请求参数变化时，缓存不能复用。系统应自动阻断增量路径并转入全量向量迁移。

解析器升级

MinerU 版本或参数变化可能改变元素和表格结果。解析契约变化时必须重新解析受影响文档，不能只复用旧 Chunk。

旧内容残留

替换或删除文档时必须从候选版本中排除旧 Chunk，并在 manifest 中记录删除和替换原因。

校对资产不一致

修正层、结构化表和解析文档必须使用同一候选版本快照，不能引用活动版本之外的草稿。

并发重建

同一数据根只允许一个构建租约；新任务应排队或拒绝，不能同时写入同一个缓存和版本目录。

版权与来源

上传或导入流程需要记录来源、权利状态和展示权限。增量能力不会自动赋予原始扫描 PDF 的传播权利。

8.1 必须保留的质量门禁

  • manifest 与实际文档、Chunk、图片、向量条目数一致。
  • 活动版本的 Embedding 模型、维度和集合契约一致。
  • 新增、变化、删除文档的命中结果符合变更预期。
  • 100 条常规检索和 12 条结构化检索继续执行；增量路径不能跳过全局回归。
  • 复杂表、公式和页面证据的来源路径仍指向候选版本中的正确资产。
  • 门禁失败不更新 active_db.json，旧在线状态不被污染。

九、实施计划

以下状态按代码、自动化测试和运行证据分别标记；真实性能对照尚未完成。

  • 已完成资产指纹契约：manifest 已记录解析器与源码契约、校对修订、结构化表修订、Embedding/索引契约和逐文档变更分类。
  • 已完成文档资产缓存：从已通过门禁的不可变活动版本复用解析 JSON、规范化 Chunk、图片、MinerU 产物和审计结果；复用前校验文件与产物哈希。
  • 已完成Embedding 缓存：以活动版本的精确向量索引作为可信缓存，按稳定 Chunk ID 复用，并校验模型、维度、格式、有限值与非零向量。
  • 已完成增量候选构建器：已实现新增、未变化、变化和删除四类输入，变化文档内部仍可复用未变化 Chunk 的向量。
  • 已完成候选检索验证：仍完整生成 Chroma 记录层和独立 dense 索引，并继续执行候选运行时、100 条常规与 12 条结构化门禁。
  • 已完成后台入口：管理台已提供变更预检、增量候选重建与强制全量重建选择；当前输入边界仍是服务器源目录，浏览器上传不在本轮范围。
  • 已完成失败恢复与并发控制：复用现有单执行器、候选目录、门禁阻断、活动指针回滚和版本保留策略；缓存索引发布失败不会污染活动版本。
  • 待实施性能对照：使用现有规范集和扩展数据集比较全量与增量的解析耗时、Embedding 调用数、磁盘占用和门禁耗时。

十、验收标准

类别验收条件
功能新增一份 PDF 时只调用新增文档的解析和 Embedding；未变化文档的缓存被复用。
替换替换同名 PDF 后，旧 Chunk 不再出现在候选检索结果中，manifest 的哈希和版本发生变化。
删除删除文档后，候选版本不再返回该文档；旧活动版本仍可回滚。
一致性候选数据库、BM25、解析文本、图片、结构化表、manifest 和页面证据属于同一版本。
门禁增量候选仍执行现有候选激活门禁和全局检索回归，失败不切换活动指针。
契约Embedding 模型、维度或解析器契约变化时，系统拒绝错误复用并明确转入全量路径。
运维后台能展示变更清单、复用数量、重新解析数量、重新向量化数量、失败原因和候选版本位置。
安全当前服务器源目录输入经过 PDF 发现、路径和哈希处理；不把原始 PDF 或 API Key 写入日志和 Git。浏览器上传及其大小、来源权限审批不在本轮验收范围。

十一、待决策事项

  1. 是否把浏览器上传纳入同一轮改造，还是先支持服务器目录中的增量导入。
  2. 向量缓存采用单独 JSON/二进制资产，还是改用专门的缓存数据库。
  3. 文档被替换后，是否要求人工重新确认所有复杂表和高风险解析项。
  4. 新增规范是否默认触发完整回答级评估，还是先执行候选检索门禁再由发布人确认。
  5. 缓存和历史候选版本的保留时长，以及原始 PDF 是否允许进入运行知识包。
  6. 达到什么文档数量、Chunk 数或构建时长后，启动索引分片方案。
当前边界：增量候选重建、变更预检和 Chunk 向量复用已经实现；浏览器上传、索引分片和真实规模性能对照仍未完成，不能由本报告推断为已具备。
