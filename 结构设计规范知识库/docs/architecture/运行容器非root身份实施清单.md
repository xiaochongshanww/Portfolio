## 背景

I-046 已最小化发送给 Docker builder 的输入，但最终 API 仍以 root 运行，运行依赖安装在 `/root/.local`。一旦应用、依赖或管理接口被利用，进程会直接获得容器内最高权限；同时简单增加 `USER` 会让依赖不可读或让 Linux 绑定卷不可写，因此需要把依赖位置、镜像用户和宿主机 UID/GID 对齐作为同一项工程改造。

## 目标

最终运行镜像不以 UID 0 启动，Python 运行依赖位于与 root 家目录无关的只读虚拟环境。镜像内写目录归专用用户，Compose 构建可使用宿主机 UID/GID；CI 必须在真实容器中同时验证有效身份、数据目录写入、健康接口和控制台，而不是仅做 Dockerfile 字符串检查。

## 边界

- 非 root 不等于容器沙箱完整；Linux capabilities、seccomp、只读根文件系统和编排平台策略仍需按部署环境治理。
- 绑定卷的宿主机目录必须由目标 UID/GID 可写；不通过 `chmod 777` 或重新使用 root 绕过权限问题。
- 本轮不改变 API 数据模型、知识包格式或质量结论。
