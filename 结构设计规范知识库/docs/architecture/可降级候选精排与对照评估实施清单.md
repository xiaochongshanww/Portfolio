## 背景

当前检索已经完成 dense、BM25、条文号、查询意图和规范权威规则融合，但 `src/app/rerank` 仍只有空实现；配置一旦启用会在启动前被拒绝。现有调用还在 `top_k` 截断后执行，无法让精排模型比较更宽的候选池，也没有失败降级、供应商响应校验和候选级对照证据。

本轮目标不是默认打开一个外部模型，而是建立可运行、可回退、可观测、可评估的精排能力。真实模型是否改善当前 100 条评估集，必须由受控凭据下的同数据版本对照评估决定，不能由接口接通替代。

## 实施清单

- [x] 1. 固化精排架构决策与配置契约
  - 接受 [ADR 0024](../adr/0024-学习型精排采用候选池融合与失败降级.md)。
  - 明确默认关闭、支持的提供方、候选池上限、超时和融合权重。
  - 启用时校验提供方、模型、密钥与参数范围，拒绝拼写错误和必然不可用配置。

- [x] 2. 实现供应商无关接口和智谱 HTTP 提供方
  - 按官方 `/paas/v4/rerank` 契约发送查询与候选文本。
  - 限制查询、单文档和候选数量，严格校验索引、重复项和分数。
  - 不在日志、异常、评估报告或测试固定数据中保存 API Key 和完整用户查询。

- [x] 3. 将召回候选池与最终 `top_k` 分离
  - 启用精排时先保留不超过供应商上限的扩展候选池，再输出最终 `top_k`。
  - 保留现有规范权威规则排序作为基线，以加权秩融合而不是直接覆盖基线。
  - 在结果元数据中记录基线位次、模型位次、模型分数和融合分数，保持原检索分数语义。

- [x] 4. 建立失败开放与运行可观测性
  - 超时、网络错误、HTTP 错误或响应契约错误统一回退到基线排序。
  - 指标区分请求、成功、降级和耗时；结构化日志只记录候选数量、错误类型和耗时。
  - 精排失败不转化为问答失败，也不静默伪装成精排成功。

- [x] 5. 补充候选级排序评估与可读报告
  - 常规检索评估增加首个合格依据位次、MRR 和 Hit@K 指标。
  - 增加同一候选输入上的基线/精排对照工具，报告总体增退、逐用例位次变化和数据版本。
  - 对照报告不泄露密钥或整段受限原文；没有真实凭据时明确标记外部验证未执行。

- [x] 6. 完成自动化验证和生效文档同步
  - 覆盖正常响应、乱序响应、缺失候选、重复/越界索引、非法分数、超时和降级测试。
  - 通过 Ruff、全量后端测试、配置示例、依赖锁及既有工程门禁。
  - 更新配置参考、运维说明、系统架构、系统卡、文档中心和路线图。

- [x] 7. 阻断不完整的真实对照结论
  - 精排提供方发生降级时，对照工具返回失败关闭，不再把基线结果标记为有效精排结果。
  - 保留降级用例数和错误摘要，支持区分真实精排、部分降级和未启用提供方。

## 验收边界

- 工程完成只证明精排可安全接入和可比较，不证明检索质量已经提升。
- `RERANK_ENABLED` 在真实 100 条常规评估与回答级盲测证明无回归前保持默认 `false`。
- 受控供应商返回 429、超时、网络错误或响应契约错误时，真实对照必须失败关闭；当前已观察到 429，真实质量结论继续标记为待补。
- 本轮不引入本地 Cross Encoder、GPU 运行时或模型权重下载，避免破坏轻量运行知识包边界。
- 本轮不改变当前 `release_quality_status=passed`，也不绕过现有知识版本质量门禁；该状态不代表精排已证明改善。
