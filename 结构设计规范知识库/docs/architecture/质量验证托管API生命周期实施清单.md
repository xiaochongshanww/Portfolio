## 问题基线

- [x] 确认当前 `verify_quality.py` 已有 `/ready`、鉴权和请求失败语义，但标准运行仍要求人工预先启动 API。

## 实现

- [ ] 为 `verify_quality.py` 增加显式 `--manage-api` 模式，并保持现有外部 API 模式兼容。
- [ ] 托管模式只允许无凭据、无路径的 loopback HTTP 地址，端口已占用时失败关闭，不接管未知进程。
- [ ] API 子进程继承受控环境，并把同一基址注入 `ANSWER_EVALUATION_API_BASE`；模型与 API Key 不进入命令行。
- [ ] API 启动日志写入运行报告目录，所有错误摘要执行秘密脱敏。
- [ ] API 启动、验证器子进程和回收形成单一所有权；成功、验证失败、启动失败和中断路径均不遗留进程。
- [ ] 启动失败写机器可读验证报告，不能沿用或伪装上一份成功证据。

## 自动化验证

- [ ] 单元测试覆盖 loopback URL、路径/HTTPS/远程地址拒绝、端口占用和参数转发。
- [ ] 真实子进程测试覆盖健康启动、正常回收、失败退出、强制终止回退和日志脱敏。
- [ ] 进程级测试证明托管 API 使用与验证器相同的自定义端口，且无服务时不会执行 24 次注定失败的请求。
- [ ] 后端全量测试、前端门禁、三套依赖锁和 Compose 配置通过。
- [ ] 远程 CI Windows/Linux、前端、容器、OpenWebUI 和知识包任务全部通过。

## 真实质量证据
