## 背景

发布质量门禁已经校验活动数据版本、评估集哈希、指标阈值和报告新鲜度，但三份报告仍可来自不同验证时间或不同运行配置。可选精排、模型、检索权重或关键实现变化后，旧报告只要仍在七天有效期内，就可能与新报告组合成一个表面完整的结论。

本轮目标是让“同一份发布质量结论”只能由同一次完整验证、同一运行配置生成的常规检索、结构化检索和回答级盲测证据组成。缺少外部凭据仍会导致质量未通过，但不能再以历史基线报告替当前配置背书。

## 实施清单

- [x] 1. 固化证据关联决策与非敏感运行指纹契约
  - 接受 [ADR 0025](../adr/0025-发布质量证据采用同次运行身份与配置指纹.md)。
  - 定义受校验的 `verification_run_id`，由验证编排生成并贯穿三类报告。
  - 由 API 端根据非敏感配置与关键实现文件计算 `runtime_config_hash`，不包含 API Key、完整查询或回答内容。

- [x] 2. 贯通 API、后台任务和本地评估报告
  - 检索评估请求只允许携带运行 ID，配置指纹由实际执行进程写入。
  - 常规、结构化和回答评估统一写入证据上下文；手工单项评估仍可执行，但不能伪装为完整发布套件。
  - 管理状态接口只暴露契约版本与哈希，不暴露原始配置值或密钥。

- [x] 3. 强化发布质量门禁
  - 新增同次运行一致性检查，三份报告缺失、格式非法或运行 ID 不一致时阻断。
  - 新增当前运行配置一致性检查，三份报告必须与门禁执行进程的指纹一致。
  - 保留数据版本、评估集哈希、新鲜度和指标阈值检查，不能用新关联字段替代既有门禁。

- [x] 4. 完善失败语义和可读证据
  - 验证报告记录运行 ID、配置指纹和关联检查结果，便于追踪而不泄露秘密。
  - 部分跳过或 API 预检失败时，当前运行不得与旧报告拼接为通过结论。
  - 旧报告继续保留审计价值，但在生成新契约证据前发布状态保持未通过。

- [x] 5. 完成自动化验证和生效文档同步
  - 覆盖相同运行、混合运行、缺失字段、非法字段、配置漂移和无秘密泄露测试。
  - 通过 Ruff、全量后端、前端、配置示例、依赖锁和既有工程门禁。
  - 更新系统架构、系统卡、质量运营、API 参考、文档中心、路线图和验证记录。

## 验收边界

- 工程完成只证明质量证据不会跨运行、跨配置混用，不证明当前检索或回答质量已经通过。
- 受控凭据不可用时不得生成虚假通过证据；当前受控运行已通过，`release_quality_status=passed`，早期失败快照仍按历史事实保留。
- 运行配置指纹用于证据关联，不作为配置公开接口，也不能反推出 API Key。
- 本轮不改变评估阈值、评估集内容、模型供应商或默认精排开关。
