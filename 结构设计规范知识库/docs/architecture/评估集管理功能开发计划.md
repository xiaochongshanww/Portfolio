## 一、实施前基线

以下是本计划启动前的系统基线，用于解释建设动机，不是当前实现状态：后台可以浏览、筛选、分页和查看评估用例，也可以提交评估任务，但不能在页面中新增、编辑、校验、发布或回退评估集版本。管理 API 只接受服务端维护的 `regular`、`structured` 和 `answer` 标识，评估文件由服务端固定映射。

当前首轮实现已经补齐受控的草稿、校验、差异、发布、回退、审计和质量重跑联动；实际完成范围以本文件“实施状态摘要”和“本轮执行记录”为准，完整质量运行与人工验收仍未收口。

现有约束必须继续保留：

- 评估任务不能接收客户端任意文件路径、URL、网络共享路径或仓库外路径。
- 评估报告必须绑定评估集标识、修订版本、内容哈希和数据版本；评估集变化后，旧报告不能继续作为当前质量证据。
- 发布门禁仍由评估结果、数据版本、配置指纹、报告新鲜度和任务状态共同决定。
- 评估集维护不等于自动生成正确答案，也不允许通过编辑评估集把质量指标“改好”。
- 原始规范 PDF、用户个人信息、授权原件和密钥不进入评估集维护记录或 Git。

## 二、建设目标

### 2.1 目标

1. 维护者可以在后台创建评估集草稿、查看用例、修改用例、执行结构校验并查看差异。
2. 维护者可以把通过校验并经过确认的草稿发布为不可变修订版本。
3. 评估任务、评估报告和质量门禁能够准确识别所使用的评估集修订版本。
4. 评估集修改能够自动触发旧证据失效提示，并引导重新运行受影响的评估。
5. 评估集可以审计、回退和追溯，历史修订不被覆盖或物理删除。
6. 维护规则与具体问题内容解耦，不通过“办公楼”“阳台”等问题词硬编码业务答案。

### 2.2 首期不做

- 不支持任意本地路径、URL、网络共享路径或外部文件直接导入。
- 不支持多用户、角色权限、审批流和并发协作；首期沿用当前单机、单维护者边界。
- 不支持在页面中上传原始规范 PDF 或以 PDF 代替评估集编辑。
- 不自动调用模型生成问题、答案、引用或通过结论。
- 不支持直接修改已发布修订，不物理删除历史修订。
- 不改变现有评估阈值、模型供应商、检索算法或质量门禁规则。
- 不把评估集维护页面扩展成通用数据管理器。

## 三、核心概念与生命周期

评估集的“逻辑身份”和“内容修订”必须分离。

| 概念 | 说明 | 是否可变 |
| --- | --- | --- |
| `evaluation_set_id` | 稳定逻辑标识，如 `regular`、`structured`、`answer` | 否 |
| 评估集名称 | 面向维护者的可读名称 | 通过新修订变更 |
| `revision_id` | 某次完整内容的不可变修订标识 | 否 |
| `content_hash` | 规范化 JSONL 内容的 SHA-256 | 否 |
| 草稿 | 尚未发布的工作副本 | 可编辑 |
| 已发布修订 | 供评估任务使用的完整快照 | 不可编辑 |
| 评估报告 | 某次运行对某个修订的结果 | 不可改写 |

生命周期固定为：

```text
已发布修订
    -> 创建草稿
    -> 编辑用例
    -> 结构校验
    -> 查看差异
    -> 人工确认
    -> 发布新修订
    -> 标记受影响旧报告待更新
    -> 重新运行相关评估
```

校验失败、取消编辑或发布失败时，当前已发布修订继续可用；任何失败都不得半发布或替换当前事实源。

## 四、数据存储方案

### 4.1 推荐目录

首期继续使用 `DATA_DIR` 作为唯一运行数据根，不在代码中写死仓库绝对路径。建议增加以下目录：

```text
DATA_DIR/
└── evaluation_sets/
    ├── regular/
    │   ├── manifest.json
    │   ├── draft.jsonl
    │   └── revisions/
    │       └── <revision_id>.jsonl
    ├── structured/
    │   ├── manifest.json
    │   ├── draft.jsonl
    │   └── revisions/
    │       └── <revision_id>.jsonl
    └── answer/
        ├── manifest.json
        ├── draft.jsonl
        └── revisions/
            └── <revision_id>.jsonl
```

目录只是实现建议，正式实施时必须复用现有运行数据路径、原子写入、快照和恢复约束，并通过契约测试确认。

### 4.2 清单最小字段

`manifest.json` 至少记录：

- `evaluation_set_id`
- `name`
- `schema_version`
- `published_revision_id`
- `draft_revision_id`（无草稿时为空）
- `revision_count`
- `updated_at`
- `updated_by`（首期可为固定的本地维护者标识）

每个修订至少记录：

- `revision_id`
- `evaluation_set_id`
- `content_hash`
- `case_count`
- `schema_version`
- `created_at`
- `created_by`
- `parent_revision_id`
- `validation_summary`
- `published_at` 或空值

### 4.3 评估用例契约

首期应在不破坏现有 JSONL 数据的前提下，为三类评估集定义稳定字段：

| 类型 | 必填内容 | 重点校验 |
| --- | --- | --- |
| `regular` | 用例 ID、问题、期望规范/条文依据、检索约束 | ID 唯一、问题非空、依据格式正确、标签合法 |
| `structured` | 用例 ID、问题、期望表格/结构化依据、命中条件 | 结构字段完整、表格标识合法、条件可解析 |
| `answer` | 用例 ID、问题、期望回答要点、引用要求、拒答要求 | 期望字段完整、引用规则合法、敏感内容不入库 |

具体字段应从现有三个 JSONL 数据源反向整理，不在计划阶段擅自改变现有数据语义。兼容迁移必须先有字段盘点和样本快照。

## 五、后端实施方案

### 5.1 分层边界

建议新增独立的评估集服务层，不把生命周期逻辑堆进 `admin.py` 路由：

```text
API 路由
  -> 请求/响应模型
  -> 评估集仓储与生命周期服务
  -> 规范化、校验、哈希、原子写入
  -> 评估资产解析与评估工作流
```

服务层负责状态转换和不变量；路由只负责鉴权、参数解析和错误映射；评估工作流只读取已发布修订。

### 5.2 建议接口

接口名称以现有管理 API 风格为准，正式实现前必须更新 OpenAPI、生成客户端和运行时契约清单。

| 方法 | 路径 | 用途 | 状态改变 |
| --- | --- | --- | --- |
| `GET` | `/admin/evaluation/sets` | 列出评估集、当前发布修订和草稿状态 | 否 |
| `GET` | `/admin/evaluation/sets/{set_id}/revisions` | 列出修订历史 | 否 |
| `GET` | `/admin/evaluation/sets/{set_id}/revisions/{revision_id}` | 查看修订元数据和用例 | 否 |
| `POST` | `/admin/evaluation/sets/{set_id}/drafts` | 从已发布修订创建或重置草稿 | 是 |
| `PATCH` | `/admin/evaluation/sets/{set_id}/drafts/{case_id}` | 编辑一个草稿用例 | 是 |
| `POST` | `/admin/evaluation/sets/{set_id}/drafts/cases` | 向草稿新增一个用例 | 是 |
| `DELETE` | `/admin/evaluation/sets/{set_id}/drafts/{case_id}` | 从草稿删除一个用例 | 是 |
| `POST` | `/admin/evaluation/sets/{set_id}/validate` | 校验当前草稿并返回问题清单 | 否 |
| `GET` | `/admin/evaluation/sets/{set_id}/diff` | 查看草稿相对父修订的差异 | 否 |
| `POST` | `/admin/evaluation/sets/{set_id}/publish` | 发布已通过校验的草稿 | 是 |
| `POST` | `/admin/evaluation/sets/{set_id}/rollback` | 选择历史修订创建新的发布修订 | 是 |

接口约束：

- `set_id` 只能来自服务端允许的评估集注册表；未知类型返回 404 或 422。
- 编辑只能作用于草稿；对已发布修订的编辑请求必须失败关闭。
- 发布必须要求校验结果仍对应当前草稿哈希，防止“校验后又修改”。
- 发布操作必须幂等，重复请求不能生成不一致的半成品。
- 回退不是删除或重命名旧版本，而是从历史修订派生新的发布修订。
- 任何错误响应不得回显服务器绝对路径、密钥或原始受限材料。

### 5.3 校验规则

校验分为三层：

1. **结构校验**：JSONL 可解析、字段类型正确、必填字段存在、ID 唯一、枚举值合法。
2. **语义最低校验**：问题非空、期望依据非空、引用/表格字段之间关系完整、禁止明显占位文本。
3. **质量前置校验**：用例数量变化、类型分布变化、空答案比例、重复问题比例和高风险变更提示。

校验器只能发现结构和可机器判断的问题，不能替代结构工程专业人员判断答案是否正确。对于疑似大范围修改，应显示差异并要求人工确认，不以规则自动批准。

### 5.4 与现有评估工作流的衔接

- `resolve_evaluation_asset()` 继续接受稳定的 `evaluation_set_id`，默认解析当前已发布修订。
- 评估任务完成时把 `evaluation_set_id`、`evaluation_set_revision_id` 和 `evaluation_set_hash` 写入报告；任务入口仍只接收稳定的评估集逻辑 ID，由服务端解析当前已发布修订。
- 运行中的任务读取已固化的修订快照；发布新修订不能改变运行中任务的输入。
- 发布新修订后，旧修订报告保留为历史证据，但质量状态标记为“评估集已更新，需重跑”。
- 只有使用当前活动数据版本、当前评估集发布修订和当前配置指纹的报告，才可参与质量门禁。
- 评估集结构校验失败时，不创建评估任务，不覆盖旧报告，不改变当前活动版本。

## 六、后台页面方案

### 6.1 信息架构

新增独立的“评估集管理”工作区，职责与“质量验证中心”分离：

- **评估集管理**：维护用例、检查并发布修改、查看版本记录和恢复历史版本。
- **质量验证中心**：查看质量门禁、运行评估、比较报告和发布阻断项。
- **评估集浏览器**：可作为质量验证中心的只读证据浏览区，不承担编辑职责。

### 6.2 页面区域

当前页面包含：

1. 评估集目录：名称、用途、当前版本、已发布用例数、未发布修改状态和最近更新时间。
2. 单集工作区：按“用例 / 版本记录 / 发布”三个页签组织任务，不同时展开全部状态。
3. 用例页签：搜索、类型筛选、稳定分页和结构化表单编辑；高级 JSON 只作为扩展字段和格式诊断入口。
4. 版本记录页签：只读查看当前和历史版本，内部 ID 与内容哈希收纳在追溯详情中；恢复历史版本不会覆盖原记录。
5. 发布页签：展示未发布修改、修改内容、结构检查结果和发布确认；发布后提示前往质量验证重新运行受影响评估。
6. 质量验证入口：从单集工作区显式跳转，不在评估集编辑页面直接运行评估。

按钮状态必须与内部生命周期一致：没有未发布修改不能发布，检查失败不能发布，内容变化后必须重新检查，发布中禁止重复提交。

### 6.3 页面不变量

- 页面上使用“开始编辑”“未发布修改”“检查修改”“发布修改”“版本记录”等用户任务语言，不直接暴露 `draft` 等内部状态名。
- 页面上优先显示当前可读版本和发布状态，内部修订 ID 与哈希只作为次要追溯信息。
- 业务用户可读名称优先，内部 ID 和哈希作为次要追溯信息。
- 发布按钮旁必须展示将使哪些质量报告待更新。
- 未保存编辑、检查失败和发布失败必须有可见反馈。
- 不使用问题关键词驱动的隐藏按钮或特定问题分支。

## 七、质量、审计与安全

### 7.1 质量证据规则

评估集内容或 schema 变化视为质量输入变化，至少触发：

- 重新计算评估集哈希。
- 旧报告状态转为“历史/待更新”，而非删除。
- 质量门禁显示具体阻断项和重跑动作。
- 相关评估任务使用新发布修订重新执行。
- 评估报告记录变更前后修订关系，便于比较回归。

发布事件写入 `evaluation_sets/quality_refresh_queue.jsonl`。质量验证中心根据当前发布修订、内容哈希和完整报告身份计算待重跑状态；队列只保存修订和哈希等元数据，不保存评估用例正文。质量运行比较只读取通过完整性校验的运行目录，并把评估集变化与数据版本、运行配置变化分开显示。

### 7.2 生命周期状态机

| 当前状态 | 触发操作 | 成功状态 | 失败状态与保护 |
| --- | --- | --- | --- |
| 无草稿 + 已发布修订 | 创建草稿 | 草稿 `draft`，已发布修订不变 | 旧发布修订不变，不创建半成品草稿 |
| 草稿 `draft` | 编辑/新增/删除用例 | 草稿仍为 `draft`，上次校验失效 | 已发布修订不变，失败操作写审计 |
| 草稿 `draft` | 校验 | `validated`（绑定当前草稿哈希）或带错误的 `invalid` | 发布修订不变；错误摘要写审计 |
| `validated` 草稿 | 发布 | 新不可变修订 `published`，草稿清除，旧修订保留为历史 | 清单、草稿和新修订回到操作前状态；不移动活动知识库指针 |
| 已发布历史修订 | 回退 | 从历史内容创建新的不可变 `published` 修订 | 既有发布修订和历史文件不变 |
| 任意受控生命周期操作 | 进程/写入失败 | 不产生新的有效状态 | 旧清单、旧发布修订和草稿优先保持；失败事件保留错误元数据 |

评估报告状态不是评估集本身的生命周期状态：报告身份匹配当前修订、哈希、数据版本和运行指纹时为“当前”，否则为“历史/待更新”。发布或回退不会删除报告，只会通过待办和质量门禁要求重新运行。

### 7.3 审计记录

每次草稿创建、用例修改、校验、发布、回退和失败都应记录：

- 操作类型和结果。
- 评估集 ID、父修订、目标修订或草稿哈希。
- 时间、请求/任务关联 ID。
- 变更计数和校验摘要。
- 失败原因的可操作描述。

审计记录不保存完整问题答案以外的敏感材料，不保存 API Key，不保存原始 PDF 内容。

### 7.4 恢复与并发边界

首期继续按单机单维护者设计，但仍必须保证：

- 写入采用临时文件、校验、原子替换。
- 进程中断后不会留下“已发布但清单未更新”的矛盾状态。
- 清单损坏时服务拒绝发布并给出恢复提示。
- 草稿和已发布修订可通过现有运行数据快照备份与恢复。
- 未来多用户协作前必须重新设计租约、权限和冲突合并，不通过临时锁文件伪装支持。

## 十、验收标准

只有以下条件全部满足，才能把本计划对应功能标记为“已完成”：

1. 三类现有评估资产均可迁移为受控的首个发布修订，内容哈希和用例数量可复核。
2. 草稿编辑不会改变当前发布修订；校验失败不会改变当前发布修订。
3. 发布操作具备原子性、幂等性和失败恢复能力。
4. 评估任务和报告都记录评估集逻辑 ID、修订 ID 和内容哈希。
5. 发布新修订后，旧报告被明确标记为历史或待更新，不能继续通过当前质量门禁。
6. 回退通过创建新修订完成，历史记录仍完整可见。
7. 后台页面不依赖问题关键词硬编码，不直接访问服务端文件系统。
8. OpenAPI、生成客户端、前端类型、运行时契约和文档均已同步。
9. 后端测试、前端测试、类型检查、生产构建、数据恢复和隔离 API 验证全部通过。
10. 验证记录列出已知边界，且没有把页面可用误写成内容正确性或对外发布资格。

## 十一、风险与待决策事项

| 风险/问题 | 当前处理 | 触发重新决策的时间 |
| --- | --- | --- |
| 现有评估集字段并非完全统一 | 阶段 0 先盘点，兼容优先 | schema 无法统一或需要破坏性迁移时 |
| 评估集答案本身需要专业判断 | 页面只提供校验和审阅，不自动判定正确 | 引入模型生成或自动审批时 |
| 评估集包含规范事实和引用 | 继续遵守来源权利和内部研究边界 | 向第三方展示或分发评估集时 |
| 旧报告与新修订混用 | 以修订哈希和质量门禁强制隔离 | 报告格式需要跨修订比较时 |
| 单机文件存储的并发能力有限 | 首期明确单维护者 | 多用户或远程服务上线前 |
| 评估集维护可能被误用为指标调优工具 | 保留不可变历史、差异和发布门禁 | 允许外部用户编辑或自动生成时 |

以下事项仍由待决策登记管理，不由本计划默认决定：

- 是否允许第三方维护或上传评估资产。
- 是否需要角色权限、审批人和多人协作。
- 是否将评估集作为知识包的一部分对外分发。
- 是否允许评估集包含原始规范截图、页面图像或其他受版权约束材料。
