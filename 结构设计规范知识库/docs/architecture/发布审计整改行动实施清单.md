# 发布审计整改行动实施清单

> 状态：已完成
> 维护角色：发布与质量负责人
> 文档更新：2026-08-20
> 代码/流程核对：2026-08-20，审计结果、JSON 契约、Markdown 渲染和责任角色映射已核对
> 完整运行验证：外部审计为 4 个未通过检查生成整改行动；内部研究审计为 1 个非阻断提醒生成行动
> 验证证据：[发布审计整改行动验证记录](../releases/发布审计整改行动验证记录.md)、[ADR 0036](../adr/0036-发布审计输出整改行动.md)
> 复核周期：发布门禁检查项、责任边界或治理流程变化时

## 目标

发布审计不仅要说明当前是否可发布，还要把每个未通过检查转换为可执行的责任角色、处理动作和验证条件。行动建议只能帮助整改，不得改变 `ready`、阻断级别或来源资格结论。

## 实施清单

- [x] 1. 为未通过审计检查增加结构化 `remediation` 字段，包含 `owner`、`actions` 和 `verification`。
- [x] 2. 覆盖质量证据、来源资格、运行 manifest、封闭试用、交付决策和精排质量等通用检查类型。
- [x] 3. 在 Markdown 审计报告中增加“整改行动”章节，并与 JSON 使用同一结果对象。
- [x] 4. 增加 JSON 结构和 Markdown 人工阅读测试。
- [x] 5. 保持外部/内部 profile 的原有门禁结果不变，并同步路线图、文档中心、发布检查单、运维手册、架构说明和 ADR。

## 边界

- 责任角色和动作是治理流程提示，不是自动批准、法律意见或产品决策。
- 审计不会执行来源权利修改、试用记录生成、交付决策或精排供应商调用。
- 任何阻断项仍须通过原检查器或真实证据验证后，才可能改变发布结果。
