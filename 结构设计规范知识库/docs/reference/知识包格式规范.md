## 1. 用途

知识包用于在“知识资产生产环境”和“轻量问答环境”之间迁移已经构建的运行资产。它不是原始 PDF 归档格式，也不包含人工校对工作区。

导出或导入成功只表示技术完整性，不表示包内内容可以公开传播。发布者必须另行完成来源与权利审核。

## 2. 容器与目录

文件扩展名使用 `.zip`，根目录结构如下：

```text
knowledge-package.json
runtime/
  manifest.json
  db/
  metadata/
    specs.json
  structured_tables/
  images/
  raw/
```

其中 `knowledge-package.json`、`runtime/manifest.json`、`runtime/db/` 和 v3 及以上版本的 `runtime/metadata/specs.json` 为必需项。其余目录按清单中的能力声明选择性存在；`runtime/raw/` 默认不包含。

## 3. 包清单

`knowledge-package.json` 使用 UTF-8 JSON，核心字段如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `format` | string | 固定为 `structural-spec-knowledge-package` |
| `schema_version` | integer | 当前导出为 `4`；校验和导入兼容 `1`、`2`、`3` |
| `package_id` | string | v4 绑定数据版本、payload 和身份元数据；旧版算法保持兼容 |
| `profile` | string | 当前固定为 `runtime` |
| `created_at` | string | UTC ISO 8601 时间 |
| `data_version_hash` | string | 来源构建 manifest 的数据版本 |
| `payload_hash` | string | 对排序后的文件路径、角色、大小与 SHA-256 声明计算的摘要 |
| `document_count` | integer | 文档数量摘要 |
| `chunk_count` | integer | chunk 数量摘要 |
| `compatibility` | object | 应用、CPython、操作系统、架构、Chroma、Embedding 和集合信息 |
| `capabilities` | object | 数据库、表、图片、来源访问策略和原始 PDF 是否包含 |
| `quality` | object | v2 及以上版本必需；门禁时间、数据版本、失败项、报告有效期、豁免和审计事件 |
| `files` | array | 所有 payload 文件的路径、大小、SHA-256 和角色 |

清单本身不出现在 `files` 中。除清单外，ZIP 中不得出现未声明文件。

v1 包没有 `quality` 字段，只为已有包保留技术兼容。v1、v2 都不强制携带来源访问策略；它们不能证明目标环境保留了当前图片展示边界。v3 继续使用“数据版本 + payload + 质量证据”的包标识算法；v4 将清单中的格式、版本、配置、能力、质量和兼容性共同纳入身份摘要，修改这些字段而不重新生成 `package_id` 会被拒绝。

## 4. 能力声明

```json
{
  "prebuilt_vector_index": true,
  "structured_tables": true,
  "extracted_images": true,
  "source_pdfs": false,
  "page_images": false,
  "source_access_policy": true
}
```

`page_images` 只有在包含原始 PDF 时才为 `true`。缺少原始 PDF 的运行环境不得承诺 `/page-images/{doc}/{page}` 可用。v3 的 `source_access_policy` 必须为 `true`，并与 `runtime/metadata/specs.json` 同时存在。

## 5. 完整性与安全规则

1. 所有 payload 文件必须使用相对 POSIX 路径。
2. 禁止绝对路径、盘符、反斜杠、空路径、`.` 和 `..` 路径段。
3. 每个文件必须匹配清单声明的大小和 SHA-256。
4. 不允许重复路径、符号链接或未声明文件。
5. 导入必须先完整校验，再复制资产，最后切换活动数据库指针。
6. 知识包不得包含 `.env`、API Key、运行时密钥或用户凭据。
7. SHA-256 清单用于发现损坏和非预期改动，不提供发布者身份认证；从不受信任渠道取得的包不得仅因校验通过而执行导入。
8. v2 及以上版本必须包含与 `data_version_hash` 一致的质量证据；门禁未通过时必须包含责任人和原因完整的显式豁免。
9. v2/v3 `package_id` 绑定规范化质量证据；v4 进一步绑定格式、profile、时间、计数、兼容性和能力声明。
10. v3 及以上版本必须携带来源访问策略；导入时将其安装到 `data/metadata/specs.json`，不得用缺省公开策略替代。

## 6. 兼容性

运行包携带预构建 Chroma 数据库。`package-validate` 会比较应用主版本、Python 主次版本与实现、Chroma 主版本、操作系统、处理器架构、Embedding 模型和集合名称；`AMD64`、`x64` 与 `x86_64` 统一为 `x86_64`，`arm64` 与 `aarch64` 统一为 `aarch64`，避免等价名称造成误报。

当前自动验证矩阵是 CPython 3.11、Chroma 1.5.9、x86_64 的 Windows 与 Linux 双向迁移。矩阵外组合只能视为未验证，不能由“哈希校验通过”推断可运行。目标环境必须执行：

```powershell
python -m src.pipeline package-validate --package dist\knowledge-runtime.zip
python -m src.pipeline package-probe --package dist\knowledge-runtime.zip
```

`package-probe` 会在临时数据目录中导入知识包，并在隔离子进程中实际打开 Chroma 集合、核对记录总数和读取一条样本；探测不会切换项目当前活动数据库。CI 使用 `--expect-source-platform` 和 `--require-cross-platform` 强制证明来源与目标操作系统不同，并只允许预期的操作系统差异告警。对外分发、其他架构、macOS 或 Chroma/Python 版本升级仍需单独决策和验证。

## 7. 生命周期

- 导出：读取活动数据库和对应 manifest，实时计算质量门禁；通过或完成显式豁免审计后，收集运行资产并生成哈希清单。
- 校验：不写入本地数据，只检查格式、路径、文件声明、哈希、身份元数据和静态兼容告警。
- 运行探测：在临时目录隔离导入并打开预构建索引，完成目标环境的真实可读性检查，不激活在线数据库。
- 导入：安装为独立数据库版本，复制可选资产，更新根 manifest 和活动数据库指针。
- 激活后：重启或重载 API，再执行健康检查与质量门禁。
- 回退：恢复之前的 `active_db.json` 和 manifest；可选资产冲突必须使用导入前备份恢复。

具体命令和操作限制见 [部署运行手册](../operations/部署运行手册.md)。
