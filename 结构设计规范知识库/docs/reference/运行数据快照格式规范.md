## 1. 用途与边界

运行数据快照用于在停机维护窗口完整备份和恢复一个 `DATA_DIR`。它包含原始 PDF、数据库版本、任务、审计、修正、人工结构化资料、质量报告、图片、来源策略和其他位于数据根内的普通文件，与只携带问答运行资产的知识包用途不同。

快照是高敏内部运维工件，不是可分发知识包。校验成功只证明格式和内容完整，不证明来源资料可以传播，也不提供发布者身份认证、加密或恶意内容信任。

## 2. 容器与清单

文件使用 ZIP64，根目录只有清单和声明的文件负载：

```text
runtime-backup.json
data/
  ... DATA_DIR 的完整普通文件内容 ...
```

空目录不作为 ZIP 目录成员写入，而是在清单 `directories` 中声明并在恢复时重建。schema v1 的核心字段如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `format` | string | 固定为 `structural-spec-runtime-backup` |
| `schema_version` | integer | 当前固定为 `1` |
| `backup_id` | string | `rb-` 加规范化 inventory 哈希前 24 位 |
| `created_at` | string | 带时区的 UTC ISO 8601 时间 |
| `actor` | string | 创建责任人，不进入内容身份 |
| `source_scope` | string | 固定为 `DATA_DIR`，不保存主机绝对路径 |
| `root` | object | 数据根的 `mtime_ns` 和权限 `mode` |
| `directories` | array | 按路径排序的完整目录声明，含元数据 |
| `files` | array | 按路径排序的文件路径、大小、SHA-256 与元数据 |
| `payload_hash` | string | 规范化文件路径、大小和内容哈希摘要 |
| `inventory_hash` | string | 根、目录和文件完整声明摘要 |
| `file_count` / `directory_count` | integer | 声明数量 |
| `uncompressed_size_bytes` | integer | 所有文件负载大小之和 |

`backup_id` 不受输出文件名、创建时间或责任人影响；同一文件内容但修改时间、权限或空目录不同，会形成不同身份。

## 3. 创建协议

```powershell
python -m src.pipeline backup-create `
  --data-dir $env:DATA_DIR `
  --output D:\backups\structural-kb-20260808.zip `
  --actor operator `
  --maintenance-window
```

创建要求 API 已停止并显式传入 `--maintenance-window`。工具拒绝：

- 输出位于源 `DATA_DIR` 内；
- 源根或任意成员是符号链接、重解析出的链接或其他特殊文件；
- `data/jobs` 中存在无法解析记录或 `queued`/`running` 任务；
- 输出已存在且没有 `--overwrite`；
- 两次完整扫描之间出现文件、目录、内容或元数据变化。

工具先计算完整清单，再写临时 ZIP，重新扫描源并离线校验临时 ZIP，全部一致后才原子替换输出。失败时删除临时输出。

## 4. 离线校验

```powershell
python -m src.pipeline backup-validate --backup D:\backups\structural-kb-20260808.zip
```

校验不读取或写入当前 `DATA_DIR`。它检查 ZIP 完整性、解压总量、路径穿越、盘符、重复成员、ZIP 符号链接、规范排序、完整父目录、文件声明、大小、SHA-256、总量、payload/inventory 哈希和 `backup_id`。默认解压总量上限为 100 GiB。

## 5. 事务恢复

恢复到空数据根：

```powershell
python -m src.pipeline backup-restore `
  --backup D:\backups\structural-kb-20260808.zip `
  --data-dir $env:DATA_DIR `
  --actor operator `
  --maintenance-window
```

替换现有非空数据根还必须显式添加 `--replace`。工具先完整校验归档并在目标父目录解压，恢复文件/目录元数据和哈希；之后把原目标原子移动到同文件系统临时目录，再安装新目录。安装或复核失败时自动搬回原目录。若自动回退本身失败，工具保留临时目录并在错误中给出旧数据位置，不会清理唯一副本。

快照文件不能位于目标 `DATA_DIR` 内。目标或快照中的活动/损坏任务都会阻断恢复。恢复成功后必须重启 API，并核对配置预检、`/health`、`/ready`、活动数据库身份、质量状态和任务启动对账。

## 6. 存储与生命周期

1. 快照 ZIP 本身不加密、不签名；必须存入具备静态加密、最小权限、版本控制和删除审计的受控存储。
2. 至少保留一份与运行主机隔离的副本，并定期在隔离目录执行 `backup-validate` 和恢复演练。
3. 快照不会包含项目根 `.env`、`.runtime_api_key`、Open WebUI 命名卷或仓库外日志；这些资产需要各自的备份与秘密恢复方案。
4. 若操作者把凭据或其他敏感文件放入 `DATA_DIR`，完整快照会如实包含，工具不会按文件名猜测并删除。
5. 恢复后的预构建 Chroma 仍受应用、Python、数据库版本和平台兼容矩阵约束；完整性校验不转换数据格式。
