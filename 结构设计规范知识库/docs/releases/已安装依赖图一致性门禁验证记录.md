## 验证目标

证明项目不仅能从精确哈希锁重建依赖，还会在每个受控 Python 环境安装完成后验证所有已安装包的声明约束。检查必须位于测试、产包、恢复或镜像复制之前，且不能破坏最终运行镜像主动移除 pip 的最小化边界。

## 测试先行

新增契约测试按 workflow job 分块读取双平台后端、产包和跨平台恢复任务，并分别验证安装、`python -m pip check`、核心工作三者的顺序；Docker 契约另行验证 builder 安装后检查、最终镜像移除 pip 和站点包复制顺序。实施前两项测试均按预期失败，分别指出 workflow 与 Dockerfile 缺少检查。

## 实施结果

- 双平台后端任务安装开发锁后执行 `pip check`，再进入 Ruff、OpenAPI 和 595 项测试；
- 双平台产包任务安装运行锁后执行 `pip check`，再创建真实 Chroma 知识包；
- 两条跨平台恢复任务安装运行锁后执行 `pip check`，再下载、导入与冷启动异平台知识包；
- Docker Python builder 安装运行锁后执行 `pip check`，最终阶段仍卸载 pip、setuptools、wheel 与辅助包；
- README、部署手册和系统详细设计已区分锁可复现、哈希安装与已安装图一致性三层责任。

常规 CI 不安装重型 PDF 解析锁。知识生产环境安装解析锁后应执行同一命令，再运行解析器兼容自检；这属于实际生产环境验收，不以普通 CI 的字符串检查冒充覆盖。
