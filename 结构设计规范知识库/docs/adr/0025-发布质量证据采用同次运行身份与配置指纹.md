# ADR 0025：发布质量证据采用同次运行身份与配置指纹

> 决策日期：2026-08-09
> 关联评估/发布：I-035
> 验证证据：[实施清单](../architecture/质量证据运行身份与配置指纹实施清单.md)、[验证记录](../releases/质量证据运行身份与配置指纹验证记录.md)
> 复核周期：质量编排、运行配置、评估报告或发布门禁契约变化时

## 背景

现有发布门禁分别读取常规检索、结构化检索和回答级盲测的 `latest` 报告，并校验数据版本、评估集哈希和七天新鲜度。这不能证明三份报告来自同一次验证，也不能证明它们对应当前检索权重、模型、精排开关和关键实现。配置可变能力增加后，跨运行拼接证据会产生错误的发布结论。

## 决策

1. 完整质量验证每次生成一个 32 位十六进制 `verification_run_id`，同一次编排产生的三类报告必须携带相同值。
2. 检索评估 API 可以接收运行 ID，但 `runtime_config_hash` 必须由实际执行 API 根据当前非敏感设置和受控关键代码清单计算，客户端不能提交该哈希。
3. 运行指纹覆盖会影响检索、生成、图片证据和评估语义的配置及关键实现文件；哈希输入不得包含任何 API Key、授权头、完整查询、回答或用户内容。
4. 发布质量门禁必须同时验证三份报告的运行 ID 一致、格式有效，并与当前 API/门禁进程的运行指纹一致。
5. 数据版本、评估集哈希、指标阈值、新鲜度、任务状态和内容门禁继续独立阻断；运行身份与配置指纹不能替代这些检查。
6. 单项人工评估可以没有发布运行 ID，但其报告只能用于诊断，不能与其他历史报告组合成完整发布通过证据。
7. 旧契约报告不迁移或补写关联字段；它们保留历史审计价值，但在新门禁下自然失效。
8. `verification_run_id` 是受信任管理边界内的证据关联标识，不是签名或远程证明。系统假定管理 API、验证编排器和运行主机可信；若未来需要抵抗主机管理员篡改，应另行引入签名证据、不可变日志或外部证明服务。

## 备选方案

- 只依赖生成时间窗口：不同进程时钟、重试和并发运行仍可能混合，不能证明同一次编排。
- 只比较数据版本：无法识别检索权重、模型、精排开关或实现变化。
- 允许客户端提交配置指纹：客户端可以误报或伪造，不能证明实际执行环境。
- 把全部配置写入报告：可读但增加敏感信息和部署细节泄露面，没有必要。

## 影响

- 已有报告会新增关联检查失败，直到在完整、具备受控凭据的环境重新执行三类评估；这是预期的失败关闭行为。
- 质量验证、管理 API、后台评估工作流、质量门禁和知识包导出共享同一证据契约。
- 修改受控配置或关键代码后，既有质量报告即使仍在时间有效期内也不能继续为新运行时背书。
- 增加的字段均为随机运行标识、契约版本和不可逆哈希，不新增秘密持久化。
- 具备管理权限的操作者仍可主动复用运行 ID；门禁防止的是误拼接、陈旧证据和配置漂移，不声称防御已控制运行主机的恶意主体。

## 回退

若关联实现导致运行故障，可回退代码并恢复旧门禁，但不得手工删除新检查或补写伪造字段来获得通过。回退后生成的质量结论必须明确采用旧证据契约，且不能作为当前版本发布证据。
