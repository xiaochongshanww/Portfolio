## 背景

当前检索的规范领域规则可以判断正文、表格和条文说明的权威差异，但候选间的自然语言相关性仍主要依赖 dense、BM25 和通用内容词匹配。仓库已经预留 reranker 接口，却只有空实现，并且在最终 `top_k` 截断之后调用；这既不能比较更宽候选，也无法证明学习型精排相对基线的收益。

本项目的运行知识包强调轻量部署。直接引入本地 Cross Encoder 会增加模型权重、推理框架、CPU/GPU 要求、许可证和离线分发负担。智谱提供独立文本重排序 HTTP API，单次支持最多 128 个候选，当前运行依赖已经包含 HTTP 客户端和同供应商密钥，但外部模型仍有费用、时延、限流和可用性风险。

## 决定

1. 精排默认关闭，只支持显式提供方。第一种提供方通过智谱官方 HTTP `/paas/v4/rerank` 接口实现，不把未确认的 SDK 私有接口作为运行契约。
2. 启用精排时，混合检索先生成大于最终 `top_k`、且不超过 128 条的候选池。精排只影响候选池次序，不改变召回源、原始检索分数和知识内容。
3. 现有规范权威规则排序是基线先验。模型结果与基线位次采用可配置、确定性的加权秩融合；不允许供应商分数直接覆盖规范领域基线。默认模型权重低于基线权重。
4. 请求文本包含规范名、编号、标题、条文号、依据类型、表号和截断后的候选正文，使模型能比较直接依据；查询和单候选均限制为供应商声明的 4096 字符。
5. 提供方响应必须校验结构、候选索引唯一性和范围、分数有限性。未返回的候选按原基线顺序补回，不因部分响应丢失证据。
6. 超时、网络、鉴权、限流、HTTP 错误和响应契约错误全部失败开放到基线排序。降级会写入聚合指标和不含查询正文的结构化日志；问答请求不因可选精排不可用而失败。
7. 精排工程完成与质量启用分开判定。只有同一数据版本、同一评估集和同一候选输入上的对照评估证明主要指标无回归，才可在具体环境启用；仓库默认值仍保持关闭。

## 备选方案

- 直接使用供应商排序：实现简单，但可能再次让语言完整的条文说明压过正文表格，违背规范权威排序目标，因此拒绝。
- 在最终 `top_k` 上精排：不能挽回提前截断的直接依据，也无法形成真实精排候选空间，因此拒绝。
- 本地部署 Cross Encoder：可离线运行，但显著增加镜像、硬件和模型治理负担；当前没有质量收益与运行成本证据，暂不采用。
- 精排失败关闭整个问答：会把可选质量增强变成单点故障；已有基线检索可用，因此采用失败开放并明确可观测。
- 默认开启外部精排：缺少真实 100 条评估和回答盲测证据，且会产生新费用与时延，暂不采用。

## 后果

- 运行时在启用精排的环境中会增加一次外部 HTTP 调用和相应 token 成本；默认部署不发生该调用。
- 供应商看到经过截断的用户查询和候选文本，部署方必须按 AI 服务治理政策确认数据处理与留存边界。
- 候选池扩大可能增加本地排序和外部请求时延，因此数量、超时和模型权重必须配置并纳入评估。
- 失败开放保护可用性，但可能使同一问题在供应商故障前后出现排序差异；指标必须能识别降级比例。
- 新实现不会改变当前质量结论，也不代表外部模型、费率、SLA 或数据合规已经获得批准。

## 验证与回退

- 使用模拟 HTTP 传输覆盖请求格式、合法响应、部分响应、重复/越界索引、非法分数、HTTP 错误和超时。
- 用检索集输出 MRR、Hit@K 和逐用例首个合格依据位次，并支持同候选输入对照。
- 启用后若降级率、时延或质量指标不满足环境要求，将 `RERANK_ENABLED=false` 即可恢复既有基线，不需要重建知识库。
- 真实供应商验证必须绑定 API 提供方、模型名、数据版本、评估集哈希和执行时间，不能用模拟测试替代。
