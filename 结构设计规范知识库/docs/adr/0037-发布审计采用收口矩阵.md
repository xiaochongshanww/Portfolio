# ADR 0037：发布审计采用收口矩阵

> 状态：已接受
> 决策日期：2026-08-20
> 维护角色：发布与质量负责人
> 文档更新：2026-08-20
> 代码/流程核对：已核对 `audit_release_readiness.py`、JSON/Markdown 测试和现有发布门禁
> 完整运行验证：收口矩阵已验证；外部发布资格仍未就绪
> 验证证据：[发布审计收口矩阵验证记录](../releases/发布审计收口矩阵验证记录.md)、`tests/test_release_readiness.py`
> 关联评估/发布：I-054；[发布检查单](../releases/发布检查单.md)
> 复核周期：审计检查项或整改责任边界变化时

## 背景

I-053 已为未通过检查提供责任角色、整改动作和验证条件，但这些信息仍嵌套在各个 `checks[]` 项中。发布负责人需要同时阅读阻断明细、整改行动和路线图，容易遗漏某个未闭合证据。

## 决策

审计结果在保留原有 `checks`、`blockers` 和 `warnings` 的同时，增加只读的 `closure` 汇总对象：

- `ready`、开放项和阻断/提醒计数；
- 阻断与提醒的检查编号；
- 每个未通过检查的状态、说明、责任角色、整改动作和验证条件。

Markdown 报告从同一对象渲染“收口矩阵”。该对象不拥有独立决策权，也不允许覆盖原检查结果。

## 后果

- 发布负责人可以按责任角色和验证条件逐项交接人工补证。
- 后续控制台或工单工具可以消费稳定的汇总结构，不必解析 Markdown。
- 真实来源权利、试用反馈、精排质量和产品决策仍必须由对应原始证据关闭；当前外部审计结论不会因增加汇总层而改变。
