# ADR 0001：使用运行知识包解耦构建与问答

> 决策角色：工程负责人  
> 关联评估/发布：2026-08-08 已完成后端测试、知识包往返测试和运行时加载验证  
> 验证证据：`tests/test_knowledge_package.py`、`docs/reference/知识包格式规范.md`、`docs/releases/运行知识包首次验证记录.md`  
> 复核周期：架构边界或知识包格式变化时

## 背景

完整知识资产生产依赖 PDF 解析、MinerU、人工校对、复杂表结构化、向量化和质量评估。普通使用环境只需要活动向量库、manifest、结构化表、图片和可选原始 PDF。若要求每个使用者重复安装构建环境，不仅门槛高，也混淆了内容生产者和问答使用者的责任。

项目当前不以长期商业化 Web 服务为前提，因此需要一种可在受控环境之间迁移已构建知识资产的方式，同时避免默认分发原始扫描 PDF。

## 决定

引入版本化 ZIP“运行知识包”，用于把已验证的运行资产从构建环境迁移到问答环境。

- 必需内容：包清单、构建 manifest、预构建 Chroma 数据库。
- 可选内容：已发布结构化表、解析图片、原始 PDF。
- 原始 PDF 默认不导出，必须通过显式参数加入。
- 包清单记录文件大小和 SHA-256；`package_id` 同时绑定数据版本与实际 payload，导入前必须校验全部声明文件，拒绝未声明文件和不安全路径。
- 导入的向量库安装到独立版本目录，校验和资产复制完成后才更新活动数据库指针。
- 导入不包含 API Key、运行日志、校对候选、人工草稿或其他维护环境状态。
- 预构建 Chroma 数据库用于同类运行环境快速启动；清单必须记录 Chroma、Embedding 和集合信息，版本不一致时给出兼容性警告。

知识包是否允许对外分发属于内容权利决策，不由技术实现自动推定。导出成功只证明文件完整，不证明内容获得授权。

## 备选方案

1. 每个使用者从 PDF 完整重建：内容边界清晰，但 MinerU、硬件、人工校对和命令行门槛过高。
2. 永久托管统一 Web 服务：使用门槛低，但需要持续承担服务器、模型、安全、内容托管和运营责任。
3. 只分发 chunks 并在目标环境重新生成 Embedding：可移植性更好，但首次运行仍需要 Embedding Key、费用和较长构建时间。保留为未来的“可移植知识包”配置，不阻塞本次运行包实现。

## 后果

- 构建环境和问答环境可以独立部署，目标环境不需要 MinerU。
- 知识包能够承载已校对和已结构化结果，但文件体积可能较大。
- Chroma 文件格式和 Embedding 模型形成运行兼容约束，升级时需要重新验证或重新构建。
- 默认排除原始 PDF 后，`/page-images` 不一定可用；系统应优先使用包内解析图片，并明确能力状态。
- 任何知识包发布仍需来源登记、展示权限和内容治理审核。
- 当前哈希清单不提供发布者身份认证；面向非受控渠道分发前需要设计包签名和信任根。

## 验证与回退

- 自动测试覆盖导出、哈希校验、路径穿越拒绝、导入、冲突处理和活动指针切换。
- 在临时目录完成真实数据包导出与验证；不在验证阶段覆盖当前活动数据。
- 导入失败时不更新活动数据库指针；已复制的新文件应回滚或保持为未激活版本。
- 若运行知识包方案不能稳定跨环境工作，可继续保留现有本地构建流程，并新增 chunks 级可移植配置替代预构建数据库。
