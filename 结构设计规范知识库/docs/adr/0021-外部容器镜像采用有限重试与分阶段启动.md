## 背景

提交 `3abfb58` 触发的 CI #75 中，应用镜像构建成功，但 OpenWebUI 集成任务在执行 `docker compose up` 时拉取 `ghcr.io/open-webui/open-webui:v0.9.5`，被上游仓库以 `toomanyrequests` 拒绝。该任务在不改代码的情况下重跑后通过，证明这是外部瞬时故障，不是 Compose 或应用回归。

当前启动命令把“拉取外部镜像”和“创建容器”合并在同一步。一次仓库限流、TLS 握手超时或短暂网络中断会直接使整条门禁失败；日志也不能稳定区分镜像不可用、永久配置错误和容器启动错误。

## 决策

1. 提供跨平台 Python 入口，显式执行 `docker compose pull --ignore-buildable`，由调用方声明要拉取的服务，不在实现中绑定 OpenWebUI 或某个业务问题。
2. 只对受控的容器仓库瞬时错误执行有限重试，包括限流、超时、连接重置、临时 DNS 故障和网关临时不可用；未知错误和永久错误立即返回原退出码。
3. 重试采用有上限的指数退避；单次 Compose 调用默认设置 600 秒超时并可显式调整，超时命令由 Python 子进程管理终止，耗尽后返回 124。调用方仍应设置独立的总任务超时。每次尝试输出稳定、可读且不包含凭据的诊断事件。
4. 显式拉取成功后，Compose 启动使用 `--pull never`。拉取失败和容器创建/健康失败由不同步骤承担，避免启动阶段再次隐式访问仓库。
5. CI 使用同一仓库脚本，不在 workflow 中复制重试循环。部署手册提供同一入口，运维人员可在启动前单独完成和诊断镜像拉取。
6. 重试成功只证明镜像已取得，不替代镜像身份锁定、漏洞扫描、Compose preflight、运行健康检查或内容质量门禁。

## 备选方案

- 直接重跑整个 CI：能偶然绕过瞬时故障，但重复消耗全部已通过任务，且不能改善用户部署体验，因此拒绝作为标准流程。
- 在 workflow 中写 Bash `for` 循环：实现快，但 Windows 本地不可复用，瞬时错误分类和测试也会散落在 YAML 中，因此拒绝。
- 对所有非零退出码重试：会延迟镜像名错误、权限错误和 Compose 配置错误的反馈，因此拒绝。
- 无限重试直到成功：可能掩盖持续故障并占满 Runner 或运维窗口，因此拒绝。
- 本轮同时把所有容器镜像改为 digest：能增强可复现性，但涉及多架构清单、更新机制和安全扫描的独立决策；保留为后续容器供应链迭代，不扩大 I-031 范围。

## 兼容性与边界

- 包装器只依赖 Python 标准库和 Docker Compose CLI，可在项目支持的 Windows/Linux Python 3.11 环境运行。
- 服务名由调用者显式给出，未配置 Docker、Compose 文件无效、仓库鉴权失败或镜像不存在时不应盲目重试。
- 瞬时错误匹配属于通用基础设施规则，不包含规范名称、用户问题、模型名称或其他业务特例。
- `--pull never` 要求前置拉取步骤成功；跳过前置步骤时启动失败是预期的失败关闭行为。
- 本决策不声称上游镜像长期可用，也不改变 OpenWebUI v0.9.5 的当前兼容基线。

## 验收条件

- 单元测试覆盖首次成功、瞬时错误后成功、达到上限、单次超时、永久错误立即失败、参数错误和秘密不进入诊断输出。
- CLI 在 Windows/Linux 使用相同参数和退出语义。
- OpenWebUI CI 将显式拉取与 Compose 启动拆分，启动步骤不再隐式拉取镜像。
- 部署手册、发布检查单、系统设计、路线图和文档中心同步更新。
- Ruff、全量后端、前端、依赖锁、配置、Compose、质量证据、CI Action 和远程十任务矩阵全部通过。
