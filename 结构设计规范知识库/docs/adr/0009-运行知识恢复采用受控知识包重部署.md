# ADR 0009：运行知识恢复采用受控知识包重部署

> 复核周期：知识包格式、导入事务、运行资产布局或部署拓扑变化时

## 背景

运行知识包已经具备格式校验、隔离探针、跨平台导入和 API 冷启动能力。`package-import` 在单次命令失败时会临时备份被移动的目标并恢复，因此能够保证导入事务不会留下半成品；但导入成功后临时备份随命令结束而删除，不能作为后续发布回归的持久恢复点。

现有运维说明要求分别备份和恢复 manifest、数据库、结构化表与图片。该做法容易形成版本拼接：活动指针可能指向旧数据库，而根 manifest 或全局资产已经属于新版本。人工修改 `active_db.json` 也无法证明知识包能力、来源策略和资产内容与数据库一致。

## 决定

1. 将通过质量门禁并完成校验的完整运行知识包 ZIP 作为运行知识版本的不可变部署与恢复单元。发布记录必须保存包标识、数据版本哈希、文件校验值、目标环境探针结果和上一版包位置。
2. 升级前先对新包执行 `package-validate` 和 `package-probe`，并保留当前活动包；随后进入维护窗口、停止 API 写入与读取流量，在同一 `DATA_DIR` 使用受控覆盖导入新包，重启 API 并核对就绪、包标识、数据版本、文档数、chunk 数和实际数据库路径。
3. 回退时重新校验并导入上一版完整知识包，使用同一事务导入路径恢复数据库、根 manifest、活动指针、结构化表、图片和来源策略；重启后执行同一组运行断言。不得通过手工编辑活动指针、只复制 Chroma 目录或分别挑选资产完成回退。
4. `--replace` 只允许在维护窗口、目标包来源已核验且上一版包仍可用时执行。运行中的 API 不保证热重载；知识包内的全局资产可能在进程重启前已经更新，因此不把在线导入定义为无停机升级。
5. 导入函数的临时备份只负责单次命令的事务失败恢复，不替代持久备份、上一版知识包保留或主机级灾难恢复。
6. 自动化必须使用两个内容和数据版本不同、资产路径相同的合成真实 Chroma 包，完成 A 导入冷启动、A→B 升级冷启动、B→A 回退冷启动，并证明每次服务读取预期版本且没有外部模型调用。
7. 自动化还必须注入覆盖导入中途失败，证明原活动指针、根 manifest、版本数据库和冲突资产全部恢复。

## 备选方案

- **只切换 `active_db.json`**：不能原子恢复根 manifest 和全局资产，也无法证明被指向目录仍完整、兼容且通过质量门禁。
- **成功导入后永久保留内部临时备份**：会把导入实现变成第二套无保留策略的备份系统，难以确定清理、审计和空间边界；完整知识包已经是更清晰的版本单元。
- **立即实现在线无停机双槽切换**：当前 API、结构化表和图片仍共享单一运行目录，尚无多副本流量切换与会话排空能力；在没有真实可用性要求前引入该复杂度缺少证据。
- **依赖主机目录快照作为唯一回退**：快照适合灾难恢复，但无法独立证明包兼容性、数据版本身份和跨平台可部署性，也不便作为可移植发布证据。

## 后果

- 升级和回退使用同一条受测路径，减少数据库、manifest 与资产版本错配。
- 每次发布需要保留至少当前版和上一版知识包，并记录校验值与验证证据，占用额外存储和操作时间。
- 当前方案需要维护窗口，不承诺在线热更新或零停机。
- 知识包默认不包含原始 PDF、任务、审计、人工修正源记录和全部质量历史；这些数据仍需由 `DATA_DIR` 持久卷和独立备份策略保护。
- 该决策不改变内容授权、对外分发、签名信任根或真实生产发布决定。
