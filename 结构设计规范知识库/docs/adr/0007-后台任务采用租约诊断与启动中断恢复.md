# ADR 0007：后台任务采用租约诊断与启动中断恢复

> 状态：已接受
> 决策日期：2026-08-08
> 维护角色：工程负责人
> 文档更新：2026-08-08
> 代码/流程核对：待 I-013 实现完成
> 完整运行验证：待 I-013 本地门禁与远程 CI 完成
> 关联事项：I-013
> 验证证据：[后台任务恢复与卡滞诊断验证记录](../releases/后台任务恢复与卡滞诊断验证记录.md)
> 复核周期：任务模型、进程生命周期、执行器或部署拓扑变化时

## 背景

管理端任务保存在 `data/jobs`，但当前 `queued`、`running` 状态只由内存中的单线程执行器推进。API 进程异常退出后，队列和工作线程已经消失，磁盘状态却可能永久停留在运行中；版本保留逻辑会继续保护对应目录，控制台和质量门禁也无法区分“进程已中断”“任务仍存活”和“任务长时间没有进展”。任务 JSON 直接覆盖写入，后续加入心跳后还会产生并发写坏文件的风险。

## 决策

1. 任务状态和日志采用进程内互斥与临时文件原子替换，任务 JSON 不允许通过直接覆盖留下半写文件。
2. 每个任务记录执行器实例标识、`heartbeat_at`、`progress_at` 和 `updated_at`。心跳表示执行器进程仍在维护任务，进度时间只在步骤或状态推进时更新，两者不可混为同一信号。
3. API 启动时对账持久化任务。属于旧执行器且仍为 `queued` 或 `running` 的任务统一转为 `failed`/`interrupted`，写入稳定错误码、恢复原因和结构化日志；不自动续跑。
4. 不自动续跑是安全约束：重建、版本清理、外部 AI 调用和评估可能已经产生部分副作用。中断后保留任务记录与候选资产，由操作者核对后显式重提。
5. 卡滞诊断优先使用 `progress_at`，兼容旧任务时回退到 `started_at`/`created_at`。超过可配置阈值只标记 `stalled` 并进入质量门禁，不自动把工作线程改成失败，也不宣称已经终止执行。
6. 管理 API 返回稳定的诊断字段，控制台周期刷新任务和所选日志，并用中文状态、进度年龄和中断原因帮助判断下一步操作。
7. 当前执行契约仍是单 API 进程、单工作线程。多 worker、多副本、分布式租约、跨进程抢占、强制取消和断点续跑不属于本 ADR 已实现能力。

## 后果

- 进程重启后不会再留下永久运行中的幽灵任务，版本保护和质量门禁可恢复为真实状态。
- 长任务会产生低频心跳写入；任务存储必须保证原子性并限制刷新频率。
- `stalled` 是诊断结论，不是任务终止事实。运维人员仍需查看日志、进程和候选资产后决定是否重启服务或重提任务。
- 若未来采用多进程或分布式执行器，必须新增 ADR 替代当前单实例所有权模型。
