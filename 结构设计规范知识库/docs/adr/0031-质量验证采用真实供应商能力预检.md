# ADR 0031：质量验证采用真实供应商能力预检

> 维护角色：工程负责人

> 完整运行验证：待 I-041 完成后回填
> 决策日期：2026-08-12
> 决策角色：产品与工程负责人
> 关联评估/发布：I-041、质量运行 `ca6292684bf34b67bec6b1835ae66dce`
> 验证证据：[实施清单](../architecture/质量验证供应商能力预检实施清单.md)
> 复核周期：供应商、模型、质量预检或就绪语义变化时

## 背景

`/ready` 只检查本地知识资产、索引和模型 Key 是否存在，适合作为低成本、高频运行探针。2026-08-12 的完整质量复验中，本地就绪与管理鉴权预检均通过，但智谱 Embedding 和 MiMo 聊天接口随后都返回 HTTP 401；验证器因此执行了全部工程门禁和 24 次必然失败的回答请求后才报告前置条件失效。

把“配置存在”解释为“外部能力可用”会浪费时间和调用预算，也会让检索降级结果混入本应验证完整生产配置的发布质量证据。

## 决定

1. `/ready` 保持本地、低成本且无外部网络调用，不承担供应商凭据有效性证明。
2. 新增受管理鉴权保护的 `POST /admin/provider-probes`，分别执行一次最小 Embedding 和最小聊天请求。
3. 探测响应只返回提供方、模型、耗时、稳定状态码和必要 HTTP 状态，不返回 Key、上游响应正文或模型生成内容。
4. 完整质量验证和 `--preflight-only` 在本地就绪与管理鉴权通过后执行供应商能力探测；任一必需能力失败时，三类内容评估均不启动并以明确前置失败语义关闭。
5. 供应商探测失败不修改 `/ready` 状态，也不自动轮换凭据、切换模型或降低质量门禁。

## 备选方案

- 在 `/ready` 中直接调用供应商：能暴露失效凭据，但健康探针会产生外网依赖、费用、限流和抖动，不适合高频调用。
- 继续只检查 Key 非空：实现简单，但已被真实运行证明不能判断评估是否可执行。
- 只做一次完整问答：可以同时触发检索与 MiMo，但 Embedding 失败会被 BM25 降级掩盖，无法分别证明两项必需能力。
- 由验证器直接读取供应商 Key：破坏现有“目标 API 托管模型凭据、验证客户端只持管理 Key”的秘密边界。

## 后果

- 每次显式质量预检增加一次最小 Embedding 和一次最小聊天请求，产生少量时延和供应商调用成本。
- 管理 API 操作数增加，必须同步更新响应模型、OpenAPI、生成前端 SDK 和运行时契约清单。
- 失效、过期、限流、超时和上游不可用将以稳定分类进入预检结果，原始上游正文不会进入报告。
- 真实内容评估只有在当前生产配置的两项核心外部能力均可用时才执行，减少无意义失败运行。

## 验证与回退

专项测试覆盖两项成功、401、429、超时、上游异常、响应脱敏和验证器失败关闭；管理 API 运行时契约、OpenAPI 生成漂移、前后端完整门禁与真实失效凭据预检共同构成验收证据。

如探测端点本身造成不可接受的供应商成本，可回退为显式 `--probe-providers` 选项，但发布级完整验证仍不得在未证明外部能力可用时执行。
