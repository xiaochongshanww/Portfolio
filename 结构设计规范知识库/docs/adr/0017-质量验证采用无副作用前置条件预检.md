# ADR 0017：质量验证采用无副作用前置条件预检

> 状态：已接受
> 维护角色：质量运营与工程负责人
> 文档更新：2026-08-09
> 代码/流程核对：2026-08-09，已核对既有 API、托管 API、凭据解析、就绪与鉴权探针
> 完整运行验证：专项测试和当前活动资产真实托管预检通过；全量工程门禁与远程 CI 待 I-027 收口
> 验证证据：[实施清单](../architecture/质量验证无副作用预检实施清单.md)、[验证记录](../releases/质量验证无副作用预检验证记录.md)、`scripts/verify_quality.py --preflight-only`
> 复核周期：质量验证入口、就绪条件、鉴权模型或报告写入策略变化时
> 决策日期：2026-08-09

## 背景

完整质量验证会运行测试、检索评估、回答盲测和质量门禁，并有意覆盖 `data/audit/reports/*_latest.*`。如果操作环境缺少模型凭据、运行资产或管理 API Key，直接执行完整验证只能生成一份基础设施失败报告，既消耗时间，也可能覆盖上一份仍需分析的质量证据。

现有 `/ready` 和 `/admin/status` 已能分别判断运行依赖与访问权限，托管模式也能可靠创建并回收 loopback API，但缺少只执行这些检查的标准入口。人工查看 `.env` 不能覆盖部署平台注入、Key 文件、活动数据路径和真实 API 初始化状态，也容易泄露秘密。

## 决策

1. `scripts/verify_quality.py` 新增显式 `--preflight-only`，只解析验证客户端凭据并检查目标 `/ready` 与 `/admin/status`。
2. 省略 `--manage-api` 时检查已运行的显式 `--api-base`；带 `--manage-api` 时继续沿用 ADR 0015 的 loopback、端口所有权、环境继承和进程回收契约。
3. 预检不运行后端测试、前端构建、检索评估、回答盲测或自动质量门禁，不写入 `verification_latest`、`quality_gate_latest` 或各评估报告。托管 API 启动日志仍写入既有忽略目录，用于启动诊断，不属于质量结论。
4. 输出为 ASCII 安全的机器可读 JSON，只记录凭据来源类型、是否提供凭据、状态码、就绪原因、非秘密检查和进程回收状态，不输出 Key 原值。
5. 任何凭据加载、就绪、鉴权、启动或回收步骤失败时退出码非零；托管进程无论成功、失败或中断都必须回收。
6. 预检通过只证明完整验证的运行前置条件在该时刻成立，不证明任何评估用例或发布质量门禁通过。预检失败也只能说明环境不可执行，不能解释为模型内容质量失败。

## 备选方案

- 继续让完整验证承担前置检查：会覆盖最新报告并混淆执行失败与质量失败，因此拒绝。
- 只检查环境变量是否非空：无法证明活动数据库、manifest、BM25、集合数量、服务端配置和实际鉴权可用，因此拒绝。
- 用人工启动 API 后访问页面：不可自动化，且不能稳定记录失败语义与退出码，因此拒绝。

## 兼容性与边界

- 不带 `--preflight-only` 的既有完整验证行为、报告路径和退出语义保持不变。
- `--api-key-file`、`QUALITY_API_KEY`、`QUALITY_API_KEY_FILE`、兼容文件和 `--no-api-key` 的优先级保持不变。
- 预检不连接模型供应商，不产生模型调用费用；API 初始化可能打开本地 Chroma 和读取运行资产。
- 本能力不能生成缺失凭据、修复内容资产或替代 I-022 尚待完成的真实质量复验。

## 验收条件

- 既有 API 和托管 API 两种模式均返回结构化结果。
- 缺少模型 Key 时列出 `/ready` 原因，鉴权问题单独报告。
- 托管模式成功回收自有进程，启动失败也不留下进程。
- 预检前后现有质量报告字节哈希保持不变。
- 输出不含密钥，并可在 ASCII 控制台解析。
