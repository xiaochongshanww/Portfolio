## 背景

I-031 和 I-032 已解决外部镜像拉取失败归因、有限重试、标签漂移和不可变身份，但固定摘要只能说明“取到了声明的镜像”，不能回答最终运行镜像包含哪些系统包与 Python 依赖，也不能发现之后公开的漏洞。前端 `npm audit` 只覆盖前端依赖图，不覆盖 Debian 运行层、Python wheel 和最终镜像文件系统。

扫描器本身也是供应链输入。Aqua Security 在 [GHSA-69fq-xp46-6x23](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23) 中披露 2026 年 3 月的 Trivy 生态供应链事件，并明确推荐使用安全版本和完整提交 SHA。当前采用的 Trivy `v0.73.0` 是 GitHub 标记的不可变发行版；Linux amd64 发行归档摘要和安全安装 Action 身份记录在 `security/container-security-lock.json`。

## 决策

1. 安全门禁扫描 CI 实际构建并通过健康检查的 `structural-spec-kb:ci` 最终运行镜像；不以基础镜像标签或源目录扫描替代最终产物扫描。构建阶段未进入最终镜像的 Node、编译工具和缓存不计入运行 SBOM。
2. 每次主 CI 和每周定时运行生成 SPDX JSON SBOM，并保存包含全部严重度、已修复与未修复项的 Trivy JSON 报告。扫描器版本文本、SBOM 和报告作为同一限时 CI artifact 保存 14 天，不提交仓库。
3. 门禁阻断具有修复版本的 `HIGH` 和 `CRITICAL` OS/语言依赖漏洞。尚无修复版本的发现保留在完整报告中但不阻断，以免把无法行动的上游状态变成永久随机失败；发布负责人仍须审阅其影响。
4. `.trivyignore.yaml` 使用严格 JSON 语法（JSON 是 YAML 子集），只允许 `vulnerabilities` 列表。每个例外必须限定 `paths` 或 `purls`、设置不超过 90 天的 `expired_at`，并在 `statement` 中记录 `owner=`、`tracking=` 和 `reason=`。全局忽略、永久忽略、未知字段、重复范围和过期例外均失败关闭。
5. `security/container-security-lock.json` 固定扫描器版本、上游不可变发行版、Linux amd64 归档 SHA-256、官方事件公告、安全 setup Action 完整提交、阻断阈值、超时和证据保留期。`scripts/validate_container_security.py` 在扫描前校验锁、例外和 workflow 一致性。
6. 扫描器 setup Action 固定到官方事件处置后明确列出的安全提交 `3fb12ec12f41e471780db15c232d5dd185dcb514`，Trivy 显式固定为 `v0.73.0`，不得使用 `latest` 或可变 Action 标签。外部 Action 仍受 ADR 0018 的完整 SHA 门禁和 Dependabot 人工审阅约束。
7. 漏洞数据库会随时间更新，因此同一镜像在不同日期可能得出不同结果。这是安全情报刷新，不是构建不可复现；每次结论必须绑定 CI run、镜像 ID、扫描器版本和当次报告，不把旧的绿色结果视为永久证明。
8. 普通提交仅运行不访问外部服务的确定性策略校验；既有每周供应链任务另外比较 Trivy 最新不可变发行版、固定版本和 Linux amd64 资产摘要。发行版漂移只触发待审更新，不自动替换扫描器。

## 备选方案

- 只依赖基础镜像发行方：无法覆盖项目安装的 Python 依赖，也无法形成最终镜像清单，因此拒绝。
- 仅生成 SBOM、不阻断漏洞：可审计但不能阻止已知可修复高危问题进入交付矩阵，因此拒绝。
- 阻断所有未修复高危问题：安全立场最严格，但当前个人项目无法修复上游无补丁组件；改为完整可见、仅对可修复项失败关闭。
- 直接使用 `aquasecurity/trivy-action` 可变标签：官方曾发生标签供应链事件，不符合 ADR 0018；改用安全 `setup-trivy` 完整 SHA和显式 scanner 版本。
- 现在引入镜像签名或远程证明：需要发布者身份、密钥保管、撤销和分发渠道决策，继续受 D-003 约束，不由本轮越权决定。

## 兼容性与边界

- 扫描在 GitHub Linux x86_64 Runner 执行；本地 Windows 开发不要求安装 Trivy，但必须运行确定性策略校验。
- SPDX 和漏洞报告可能包含组件路径、版本和镜像元数据，只保存在受限时效的 CI artifact，不自动公开或提交 Git。
- SBOM 是组件观察结果，不是许可证结论、内容授权、签名、来源证明或完整软件物料证明；动态下载和运行时外部服务不一定进入镜像 SBOM。
- 绿色扫描不证明零漏洞，只证明当次数据库和策略下没有未豁免的可修复 HIGH/CRITICAL 发现。
- Trivy 的 YAML 例外能力仍由上游标记为实验性；仓库以严格 JSON 语法冻结当前最小字段子集，升级扫描器时必须先验证兼容性，不能直接扩大例外 schema。
- 本轮不改变 `release_quality_status=not_passed`、内容来源等级、知识包签名决定或公网发布状态。

## 验收条件

- 策略锁、空例外基线和确定性校验器进入仓库，覆盖非法锁、可变 Action、策略漂移、过期/过宽例外和 workflow 缺项。
- 主 CI 对最终运行镜像生成 SPDX SBOM、完整 JSON 漏洞报告和扫描器身份，并上传限时 artifact。
- 主 CI 和每周定时触发对可修复 HIGH/CRITICAL 发现失败关闭；例外为空或全部满足范围、责任、跟踪和期限约束。
- Ruff、全量后端、前端、依赖锁、配置、Compose、质量快照、Action、镜像身份和安全策略门禁全部通过。
- 远程十任务矩阵完成真实镜像扫描；若发现漏洞，先升级依赖/基础镜像或登记合规例外，再关闭 I-033。
