# ADR 0048：日常知识重建采用增量处理与完整候选发布

> 状态：已接受  
> 日期：2026-08-23  
> 维护角色：工程负责人  
> 文档更新：2026-08-23  
> 代码/流程核对：2026-08-23，已核对处理契约、逐文档分类、产物和向量复用、完整候选门禁、API 与管理台入口  
> 完整运行验证：本地 `685 passed, 1 skipped`、前端 18 项组件测试、类型检查和生产构建通过；真实规范增量性能对照待执行  
> 验证证据：[增量候选重建验证记录](../releases/增量候选重建验证记录.md)、`tests/test_incremental_build.py`、`tests/test_candidate_activation.py`、`tests/test_admin_runtime_contract.py`  
> 复核周期：解析、Chunk、Embedding、索引、候选激活或管理构建接口变化时

## 背景

原重建流程每次解析全部 PDF、为全部 Chunk 重新请求 Embedding，再构建独立候选版本。它具有清晰的一致性和回滚边界，但文档规模增长后会重复消耗解析时间、Embedding 配额和人工等待时间。

直接修改活动 Chroma 集合虽然更快，却会让解析文本、图片、向量、manifest 和在线状态在任务执行期间处于不同版本，也难以在失败后证明恢复完整。

## 决策

日常重建默认采用“增量处理、完整候选发布”：

1. 通过 PDF、元数据、已批准修正、结构化表修订和处理契约指纹，把文档分类为新增、变化、复用和删除。
2. 复用必须同时满足处理契约一致、文档指纹一致、解析 JSON/Chunk 存在、引用产物存在且 SHA-256 一致。
3. 只重解析新增或变化文档；以稳定 Chunk ID 从活动精确向量索引复用向量，只为未命中 Chunk 请求 Embedding。
4. 不修改活动数据库。所有活动文档仍被重新写入一套完整候选 Chroma 记录层和精确向量索引。
5. 候选版本继续执行运行时验证、100 条常规检索和 12 条结构化检索门禁；通过后才原子切换 `active_db.json`。
6. 旧 manifest 无处理契约、Embedding/索引契约不兼容或活动向量缓存缺失/损坏时，自动回退全量重建。
7. 管理端允许在执行前查看变更分类，并保留显式强制全量重建入口。

## 处理契约

处理契约至少包含解析后端及版本、解析参数、解析适配器、Chunk 规则、入库实现、Embedding 模型与维度、精确向量索引格式和修正开关。实现源码摘要属于契约的一部分，因此相关规则变化会使旧缓存失效。

逐文档指纹至少包含原 PDF SHA-256、规范元数据、批准修正和该规范对应结构化表修订。文件名相同不构成复用证明。

## 结果

- 无变化文档不再重复执行 PDF 解析；稳定 Chunk 不再重复请求 Embedding。
- 候选数据库仍完整生成，既有原子激活、质量门禁和版本回滚语义不变。
- 从旧版本首次切换到本方案时会进行一次全量基线构建，这是有意的安全策略。
- `data/document_cache/index.json` 是可重建的缓存索引，不是活动提交点；损坏时可丢弃并回退。
- 当前缓存来源是已通过门禁的不可变活动版本及其精确向量索引，不复制在线 Chroma 数据目录。

## 边界

- 浏览器 PDF 上传和来源权利审批不属于本 ADR；当前输入仍是服务器可访问的源目录。
- 性能收益必须通过真实增量样本记录，不能仅由实现推断为已验证。
- 结构化表发布仍有独立人工发布与回滚流程；其修订进入文档指纹，但本 ADR 不改变表发布审批语义。
