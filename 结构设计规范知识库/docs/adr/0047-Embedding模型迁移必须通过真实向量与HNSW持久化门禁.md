# ADR 0047：Embedding 模型迁移必须通过真实向量与 HNSW 持久化门禁

- 状态：已采纳
- 日期：2026-08-20
- 维护角色：架构与质量负责人
- 文档更新：2026-08-20
> 代码/流程核对：2026-08-20，已核对迁移脚本、候选激活门禁、运行时向量探针和 Chroma 持久化检查
- 完整运行验证：embedding-3 迁移候选未通过 HNSW 持久化门禁；当前活动版本仍为 embedding-2
- 验证证据：[质量证据状态](../quality/质量证据状态.json)、`data/db_versions/embedding-migration-20260820225000/` 候选迁移目录
- 复核周期：Embedding 模型、Chroma 运行库、向量维度或迁移流程变化时
- 范围：向量模型、Chroma 运行库、候选版本激活

## 背景

当前活动库包含 1635 个 chunk，使用智谱 `embedding-2`、1024 维向量。实测 `embedding-3` 接口可用，也支持显式 1024 维，但“接口请求成功”“SQLite 条目数正确”不能证明 Chroma 的 HNSW 图已经可查询。Windows 下 Chroma 1.5.9 的异步写入可能出现 `data_level0.bin` 存在而 `link_lists.bin` 仍为空的中间状态；此时 BM25、条文号和表格规则仍可能让常规评估通过，掩盖 dense 索引不可用。

## 决策

1. `EMBEDDING_MODEL` 默认保持 `embedding-2`，与当前活动库保持一致；`embedding-3` 只能通过显式迁移流程启用。
2. 迁移使用现有已验证数据库的候选副本，生成新向量后删除旧记录并重新新增正文、元数据和向量，不直接 `update` 向量。
3. 迁移流程等待 HNSW 链接文件真正落盘，不把队列剩余 0/1 条作为完成信号；进程不主动调用 Chroma Rust `stop()`，交由自然退出完成持久化。
4. 候选门禁除集合数量和检索评估外，必须执行一次真实 Embedding 查询，并要求 Chroma 返回至少一条向量结果。
5. 任一条件失败时保持旧活动指针不变，并保留候选失败证据；不得仅因 API 余额充足或维度正确而切换模型。

## 后果

迁移会产生一次完整的 embedding 调用成本和较长的索引等待时间，但能避免把“看起来构建完成、实际 dense 召回为空”的库发布为活动版本。当前 2026-08-20 迁移试验因真实大集合 HNSW 图未落盘而未激活，活动库仍为 `embedding-2`；后续仅需重新执行迁移脚本，不应手工修改活动指针。

## 验证证据

- 实测 `embedding-3` 单请求返回 1024 维向量。
- 100 条常规检索和 12 条复杂表检索的规则门禁不能替代向量探针。
- 候选迁移目录 `data/db_versions/embedding-migration-20260820225000/` 的 `link_lists.bin` 保持 0 字节，脚本已失败关闭，未激活。
