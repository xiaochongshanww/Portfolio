## 背景

当前六份活动规范的解析产物均记录为 `magic-pdf, version 1.3.12`。代码和历史安装说明却只使用抽象后端名 `mineru`，`requirements.txt` 也没有固定版本。上游 MinerU 已进入新的主版本和安装方式，CLI 名称、依赖和输出结构都可能变化。仅检查命令是否存在，不能证明它能够生成当前清洗、分块和人工校对流程所依赖的 `content_list` 与 Markdown schema。

若在重建前不校验实现与版本，系统可能先清理候选输出，再使用未经验证的解析器产生不同结构的数据。即使命令成功，结果也可能在后续阶段被错误解释，形成难以发现的知识质量回归。

## 决定

1. 将 PDF 解析能力拆分为稳定的项目后端名和可审计的外部 CLI 实现。`mineru` 仍作为项目后端标识；外部实现、版本、可执行文件路径和兼容判定必须单独记录。
2. 当前唯一已验证的生产兼容组合为 `magic-pdf==1.3.12`。默认 CLI 改为 `magic-pdf`，并提供带哈希的独立知识生产依赖锁；运行 API 和导入运行知识包不安装该重型依赖。
3. 在任何候选产物清理或 PDF 处理之前执行 CLI 存在性、`--version` 退出码、输出可解析性和兼容矩阵校验。严格策略下，缺失、超时、无法识别或未验证版本均阻断重建。
4. 为迁移试验保留显式的 `allow-unverified` 策略。该策略只能由环境变量主动开启，仍要求版本可识别，并必须把未验证状态、策略和警告写入构建 manifest 与单文档产物索引；它不构成生产兼容承诺。
5. 解析器必须在删除单文档既有产物之前再次完成或复用成功探测。失败路径不得删除该文档已有解析结果。
6. `requirements.txt` 不再作为未锁定的混合依赖入口。知识生产环境使用专用输入和锁文件，运行与开发环境继续使用各自锁。
7. 解析器主版本、输出 schema 或支持矩阵变化必须作为独立迁移：使用隔离候选目录重建、完成自动审计、结构化评估和人工抽查后，才能更新兼容矩阵。

## 备选方案

- **继续只检查命令是否存在**：无法区分历史 `magic-pdf` 与当前 MinerU，也无法阻止 schema 漂移。
- **直接固定最新 MinerU**：没有现有六份文档、复杂表和校对修正的迁移证据，不能把安装成功等同于结果兼容。
- **完全禁止未验证版本**：生产最稳妥，但会阻断受控迁移实验；显式策略加审计证据可以在不弱化默认行为的前提下保留试验通道。
- **把解析器依赖并入 API 镜像**：会显著扩大镜像、硬件和许可证边界，而运行知识包已经能够把知识生产与问答运行解耦。

## 后果

- 新环境默认得到与现有知识资产一致的解析器版本，重建失败会在写操作前暴露。
- 知识生产依赖锁较大，安装仍可能受 GPU/CPU、平台 wheel 和模型资源影响；锁定依赖不等于完成真实 PDF 性能验证。
- `magic-pdf 1.3.12` 的包元数据声明 AGPL-3.0。任何二进制分发、托管服务或商业化方案都必须单独完成许可证义务评审；技术兼容不代表取得内容或软件商业授权。
- 上游 MinerU 新版本不会自动获得生产支持，需要单独迁移和质量证据。
- manifest 能够回答“由哪个可执行文件、哪个实现、哪个版本、按什么策略构建”，便于回归定位。

## 验证与回退

实现与验收以 [PDF 解析器兼容性实施清单](../architecture/PDF解析器兼容性实施清单.md) 为准。若兼容校验导致现有构建环境无法工作，应先显式配置已验证的 `magic-pdf 1.3.12` 可执行文件；不得通过移除严格校验或恢复未锁定安装入口作为回退。
