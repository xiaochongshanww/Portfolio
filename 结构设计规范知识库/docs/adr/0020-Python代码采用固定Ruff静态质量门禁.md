## 背景

项目已在 Windows 和 Linux 持续运行完整后端测试，但尚无 Python 静态检查和格式门禁。测试只能覆盖已执行路径，不能稳定发现未使用导入、未定义名称、导入顺序、容易误用的标准库调用和格式漂移。随着模块与测试数量增长，仅依靠人工评审会使同类问题反复进入主分支。

首次基线扫描覆盖 133 个 Python 文件。在 `E4/E7/E9/F/I/B/UP` 规则下发现 109 项，其中 80 项为导入排序，另有未使用导入、`zip()` 截断语义未显式声明和旧式类型注解；Ruff 格式器按 100 字符行宽会调整 109 个文件。问题规模允许一次性建立零存量基线，无需用全局忽略掩盖历史问题。

## 决策

1. 开发环境精确固定 `ruff==0.16.2`，由现有通用依赖锁生成带哈希的 `requirements-dev.txt`；运行和 PDF 解析环境不安装 Ruff。
2. 在项目根 `pyproject.toml` 统一声明 Python 3.11、100 字符行宽、LF 行尾和检查目录 `src`、`scripts`、`tests`。
3. 首版 lint 规则启用 `E4`、`E7`、`E9`、`F`、`I`、`B`、`UP`，覆盖关键语法错误、名称与导入、常见缺陷和 Python 3.11 现代化写法。不在本轮启用需要大量主观注释或类型标注迁移的规则。
4. `zip()` 必须显式声明 `strict=True` 或 `strict=False`，由调用契约决定，不使用全局 `B905` 忽略。
5. 本地标准入口为 `python -m ruff check src scripts tests` 和 `python -m ruff format --check src scripts tests`；CI 在 Windows、Linux 后端任务中以同一精确开发锁执行两项检查。
6. 首次迁移允许 Ruff 自动完成安全 lint 修复、导入排序和格式化；涉及行为语义的修复必须人工核对并由现有测试验证。

## 结果

- Python 代码风格和常见静态缺陷形成可重复、跨平台、零存量的自动门禁。
- 格式化会产生一次较大的机械 diff，后续提交只承担自身引入的变化。
- Ruff 通过不等于业务正确、类型安全或内容质量通过；pytest、运行探针和质量证据仍是独立门禁。
- 新规则或 Ruff 版本升级必须先量化影响，再更新配置、精确锁、代码和验证证据。
