# 知识库维护与质量运营

> 状态：生效  
> 维护角色：质量运营负责人  
> 文档更新：2026-08-09
> 流程核对：2026-08-09
> 完整运行验证：流程与工程门禁已核对；最新完整质量编排未通过，不能作为发布证据
> 验证证据：`scripts/verify_quality.py`、`scripts/snapshot_quality_evidence.py`、[RAG 系统卡](../quality/检索增强生成系统卡.md) 与发布检查记录
> 复核周期：每次发布

## 标准工作流

1. 导入或更新 PDF，运行 Dry Run 和重建。重建先隔离生成候选运行资产，并在通过候选运行时、常规检索和结构化检索门禁后才激活；门禁报告保存在对应版本的 `quality/` 目录。
2. 在校对工作台审核文本、公式和普通表格修正。
3. 在结构化队列处理复杂表：
   - 确认跨页分组；
   - 生成或批量生成 AI 建议；
   - 对照页面截图检查每个数值、单位、条件和表注；
   - 应用建议后保存并校验；
   - 发布，等待结构化检索冒烟测试通过。
4. 运行常规评估和结构化专项评估。
5. 在概览的“质量运营”区域确认失败任务、待处理逻辑表和评估失败均已处置。

## 自动化边界

- AI 建议只用于减少录入工作，不会自动应用或发布。
- 发布前必须通过结构校验；发布后必须通过真实结构化检索冒烟测试。
- 冒烟失败会自动恢复上一版本，首次发布则自动撤下文件。
- 批量任务中单项失败不会阻断其他任务，失败原因保存在任务日志。

## 无人值守质量验证

本机发布前验证优先使用托管模式。先通过环境、工作目录外的秘密文件或部署平台注入完整模型配置和 API 服务端鉴权配置，再运行无副作用预检：

```powershell
python scripts/verify_quality.py --manage-api --preflight-only --api-base http://127.0.0.1:8017 --api-key-file C:\secure\quality-api.key
```

预检只加载验证客户端凭据，请求 `/ready` 与 `/admin/status`，并验证托管进程回收。它不运行测试、评估或门禁，不写 `verification_latest`、`quality_gate_latest` 和评估报告；托管启动日志仍会更新。返回非零时先根据 `reasons`、状态码和凭据来源修复环境，不应覆盖或重新解释上一份质量结论。

预检通过后执行完整验证：

```powershell
python scripts/verify_quality.py --manage-api --api-base http://127.0.0.1:8017 --api-key-file C:\secure\quality-api.key
```

托管模式只接受带显式端口的 `http://localhost`、`127.0.0.1` 或其他 loopback IP，不接受 HTTPS、远程主机、用户信息、路径前缀、查询和片段。目标端口必须空闲；脚本不会复用或终止未知监听进程。它启动自己拥有的 Uvicorn 子进程，等待 `/health`，再执行原验证流程，并在成功、失败或中断后回收 API。默认最长等待 60 秒，可用 `--api-start-timeout-seconds` 调整。

API 子进程继承当前环境，并自动把同一 `--api-base` 注入 `ANSWER_EVALUATION_API_BASE`。`ZHIPUAI_API_KEY`、`MIMO_API_KEY`、`API_KEYS` 等秘密不会进入进程参数或验证报告；错误摘要按已知秘密变量脱敏。启动日志写入 `data/audit/reports/managed_quality_api_latest.log`。启动失败会覆盖生成一份新的失败验证报告，不能沿用上一份成功证据。

关闭 API 鉴权的本地环境应显式声明无 Key，避免误用遗留兼容文件：

```powershell
python scripts/verify_quality.py --manage-api --api-base http://127.0.0.1:8017 --no-api-key
```

连接已经由部署系统启动的 API 时，省略 `--manage-api`，并显式指定同一个目标：

```powershell
python scripts/verify_quality.py --api-base http://127.0.0.1:8017 --api-key-file C:\secure\quality-api.key
```

验证器分别请求公开的 `/ready` 和受保护的 `/admin/status`。未就绪时报告列出 `reasons`；401/403 则单独报告凭据错误，两者都不会提交注定失败的后台任务。凭据优先级为 `QUALITY_API_KEY`、`--api-key-file`、`QUALITY_API_KEY_FILE`、兼容 `.runtime_api_key`，`--no-api-key` 会忽略全部来源。报告不保存 Key 值。

预检通过只代表这些前置条件在检查时刻成立，不代表 100 条常规检索、12 条结构化检索、24 条回答盲测或自动门禁通过。缺少模型凭据导致的预检失败也不是模型内容质量失败。

常规、结构化与回答评估分别使用内置标识 `regular`、`structured`、`answer`。验证器和控制台不向 API 发送本机文件路径；服务端负责映射版本化评估资产，报告写入 `evaluation_set_id`、实际路径和哈希。回答级盲测由验证器直接请求同一目标的问答与图片接口，因此 `--api-base` 不会在后台退回默认端口。控制台发起回答盲测时则使用服务端 `ANSWER_EVALUATION_API_BASE`，自定义 API 监听地址的部署必须同步设置该变量。

该命令依次执行：

1. 完整后端测试；
2. Vue 前端生产构建；
3. 100 条常规检索评估；
4. 12 条结构化专项评估；
5. 24 条回答级盲测与引用资源 HTTP 验证；
6. 活动版本 manifest、运行集合数量、必需产物、高风险审计、报告溯源和任务状态门禁。

报告写入 `data/audit/reports/`：

- `verification_latest.md/json`：完整执行结果；
- `managed_quality_api_latest.log`：最近一次托管 API 启动与运行日志，不作为质量通过证据；
- `quality_gate_latest.md/json`：自动门禁结果；
- `evaluation_latest.md/json`：常规评估；
- `evaluation_structured_latest.md/json`：结构化专项评估。
- `evaluation_answer_latest.md/json`：回答级盲测、拒答与引用完整性评估。

退出码为非零时不得把当前活动版本视为可发布。候选激活门禁通过只证明运行时一致性和检索评估通过，不等于完整发布门禁。评估报告包含知识库数据版本与评估集哈希；重建知识库、修改任一评估集或报告生成时间超过 7 天后，旧报告会自动判定为过期。回答级门禁要求总体通过率不低于90%，规范依据、证据归属、截图来源、截图HTTP与拒答关键检查必须全部通过。

每次有意保留新的质量执行结果后，运行以下命令同步脱敏证据状态：

```powershell
python scripts/snapshot_quality_evidence.py --write
python scripts/snapshot_quality_evidence.py
```

`--write` 必须在持有本地 `data/audit/reports/verification_latest.json` 和 `quality_gate_latest.json` 的受控环境运行。它只提取时间、布尔状态、失败检查、相对路径、SHA-256 和评估集数量，按“`docs/quality/质量证据历史/` 归档 → `质量证据历史索引.json` → `质量证据状态.json`”的顺序原子提交。相同输入重复执行不会增加历史文件；新的失败快照同样必须保留。

第二条命令验证归档结构与文件名指纹、重复内容、确定性索引、当前快照已归档、三份评估集和系统卡；源报告存在时再核对其哈希，干净 CI 检出则不要求提交被忽略的审计目录。历史文件和索引不得手工修改；需要纠错时保留旧证据并从新的受控报告重新生成。任何失败快照都必须在系统卡中明确标记为不可发布，不能保留旧的通过文字。Git 历史只提供内部追溯，不替代签名、可信时间戳或外部证据保全。

任务 `succeeded` 表示评估用例完整执行，不表示质量已经通过。完整执行后出现检索失败用例或回答断言失败，由报告和质量门禁判定；检索服务未就绪、目标不可达、响应无效或回答请求未完成属于执行失败，任务状态为 `failed`，同时保留报告路径和明确错误。排障时应先修复执行失败，再解读命中率或通过率。

`package-export` 会再次实时计算门禁并默认阻断失败导出。只有受控排障等例外场景才能同时填写 `--quality-waiver-actor` 与 `--quality-waiver-reason`；系统会把失败项、责任人和原因写入包清单及 `data/audit/package_exports/`。豁免只绕过自动质量条件，不绕过来源权利、人工校对、鉴权或回退要求。

本机验证通过带 API Key 的 `127.0.0.1` 管理接口运行，不占用公网请求限流额度。带有 `Forwarded` 或 `X-Forwarded-For` 的 Cloudflare 请求仍执行限流。

任务状态中：

- “未解决失败”表示某类任务最近一次结果仍然失败；
- “历史失败”只用于审计，若同类任务后来成功则不阻断门禁；
- `queued`/`running` 按 `progress_at` 计算无进展时间；旧记录回退到 `started_at`/`created_at`。默认超过 2 小时会进入“疑似卡滞”并阻断质量门禁；
- 心跳表示执行器仍在维护任务，进度时间表示步骤发生变化。仍有心跳但无进度通常应先检查外部模型、解析器或大文件步骤；心跳同时过期则检查 API 进程和任务日志；
- `PROCESS_RESTARTED` 表示 API 重启后安全收口的中断任务。系统不自动续跑；核对候选目录、输出和外部副作用后，再显式提交新任务；
- 不要手工把持久任务 JSON 改成成功，也不要因为中断任务已失败就绕过版本、回退点或最短保护期规则。

## 版本保留与清理

1. 在控制台“版本管理”查看活动版本、门禁状态、占用和保护原因；不直接在文件系统删除 `data/db_versions` 子目录。
2. 对事故证据、长期对照样本或指定回退点开启“人工固定”。损坏的固定标记按受保护处理，必须先修复标记才能清理。
3. 点击“生成清理计划”。计划只包含当时未受保护且满足期限或磁盘水位条件的版本，并保存目录指纹和策略快照。
4. 核对版本、原因和预计释放空间后确认执行。后台任务会再次读取活动指针、运行任务、固定状态和指纹；变化项自动跳过。
5. 在构建任务查看执行日志，在 `data/audit/version_retention/` 查看计划、执行报告和 JSONL 事件。`partial_failed` 或后台任务失败必须处理后再生成新计划。

默认策略保留活动版本、2 个近期回滚版本和 24 小时内变化的版本；成功版本 30 天、失败或不完整版本 7 天后才可能按期限进入计划。版本总占用超过 20 GiB 时尝试回收到 16 GiB，但不会突破任何保护条件。调整策略后旧计划自动失效。

## 人工职责

- 截图与建议逐项核对，尤其是合并单元格、图中系数、空白单元格和表注。
- 不以模型置信度代替人工判断；质量提醒和 assumptions 必须逐条处理。
- 只有确认来源页、数值、单位和适用条件后才能发布。

## 外部依赖优化

- 学习型 reranker：接口已经预留，启用前需要选定并部署可用的精排服务及基准测试。
- OCR/版面引擎升级：属于独立基础设施工作，需要模型、算力和部署环境，不在当前自动化闭环内。
- 新规范接入后应扩展评估集，不能仅依赖现有规范的历史通过率。
