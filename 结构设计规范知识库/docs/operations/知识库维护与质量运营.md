## 浏览器新增或更新规范

日常新增规范优先使用控制台“规范管理”，不再直接复制 PDF 或编辑 JSON：

1. 点击“上传 PDF”。系统流式写入暂存区，校验扩展名、PDF 头、可读页数、密码状态和 SHA-256，并按内容哈希保存。
2. 补全规范编号、名称、版本、实施日期、权利状态和来源凭证索引。网上收集或权利未确认的扫描件保持 B/unknown，不得开启公开图片访问。
3. 使用“重新校验”确认登记对象仍可读且哈希一致。替换 PDF 会新增资产版本，不覆盖当前在线版本。
4. 点击“确认变更”，核对新增、替换、下架和阻断项。C 级来源、元数据不完整、资产失效或 B/unknown 级公开图片配置会阻断构建。
5. 提交候选构建。系统固化不可变来源 revision，默认执行增量处理并生成完整候选知识版本。
6. 在“构建任务”查看日志。只有候选运行时、100 条常规检索和 12 条结构化检索门禁通过后，活动知识版本和来源 revision 才同时生效。

首次启用规范管理且目录为空时，点击“导入现有规范”建立 `data/raw` 与 `data/metadata/specs.json` 的来源基线。该操作只能执行一次；它不产生新的知识解析，也不改变现有在线索引。迁移后新增、替换和下架统一通过规范管理完成。

失败处理：上传或元数据错误可在页面修正/撤销；候选构建失败时旧在线版本保持不变，失败 revision 和任务日志保留诊断信息。不要手工修改 `data/source_catalog/catalog.json`、revision 快照或 `active_db.json`。

## 标准工作流

日常维护先在管理台“构建任务”页选择“增量候选重建”，点击“分析变更”。预检会显示新增、变化、复用和删除数量；出现“将全量回退”时应阅读原因，但不需要手工改为全量，执行器会按同一事务流程安全回退。需要基准验证或怀疑缓存时，可显式选择“强制全量重建”。

### 候选构建失败后的重试发布

如果候选构建已经生成完整版本目录和 `manifest.json`，但任务在候选门禁或激活前失败，可在“构建任务”中选中原失败的 `source_rebuild` 任务，点击“重试发布候选（复用已解析结果）”。该操作会创建新的 `source_republish` 任务，重新校验来源 revision、候选 manifest 和当前来源目录未发生变化，然后重新运行候选门禁并原子激活版本；它不会再次调用 MinerU、读取 PDF 解析输入或重新生成 Embedding。

仅在以下条件全部满足时允许重试：原任务状态为失败；候选版本目录仍完整；来源 revision 仍为失败且与候选快照一致；当前来源目录没有新增、修改、替换或下架变更；候选版本尚未激活。任一条件不满足时，应从“分析变更”开始新的增量候选重建，而不是绕过校验发布旧候选。原失败任务保留为审计记录，新任务通过 `candidate_job_id` 关联原候选；新任务失败不会改变当前活动版本。

命令行等价入口：

```powershell
python -m src.pipeline rebuild-plan --source data/raw --parser-backend mineru
python -m src.pipeline rebuild --source data/raw --parser-backend mineru --mode incremental
python -m src.pipeline rebuild --source data/raw --parser-backend mineru --mode full
```

首次从旧 manifest 使用增量模式会进行一次全量重建，用于写入处理契约和逐文档指纹。后续只有契约一致且产物完整的文档才会复用。任务完成后应核对 `rebuild_mode`、`incremental_plan.counts`、`generated_embedding_count`、`reused_embedding_count` 和候选门禁结果。删除源 PDF 只会让它从新候选版本中排除，旧活动版本在门禁通过前保持不变。

1. 导入或更新 PDF，运行 Dry Run 和重建。重建先隔离生成候选运行资产，并在通过候选运行时、常规检索和结构化检索门禁后才激活；门禁报告保存在对应版本的 `quality/` 目录。
2. 在校对工作台审核文本、公式和普通表格修正。
3. 在结构化队列处理复杂表：
   - 确认跨页分组；
   - 生成或批量生成 AI 建议；
   - 对照页面截图检查每个数值、单位、条件和表注；
   - 应用建议后保存并校验；
   - 发布，等待结构化检索冒烟测试通过。
4. 运行常规评估和结构化专项评估。
5. 在概览的“质量运营”区域确认失败任务、待处理逻辑表和评估失败均已处置。

## 自动化边界

- AI 建议只用于减少录入工作，不会自动应用或发布。
- 发布前必须通过结构校验；发布后必须通过真实结构化检索冒烟测试。
- 冒烟失败会自动恢复上一版本，首次发布则自动撤下文件。
- 批量任务中单项失败不会阻断其他任务，失败原因保存在任务日志。

## 无人值守质量验证

本机发布前验证优先使用托管模式。先通过环境、工作目录外的秘密文件或部署平台注入完整模型配置和 API 服务端鉴权配置，再运行无副作用预检：

```powershell
python scripts/verify_quality.py --manage-api --preflight-only --api-base http://127.0.0.1:8017 --api-key-file C:\secure\quality-api.key
```

预检只加载验证客户端凭据，请求 `/ready`、`/admin/status` 与受保护的 `POST /admin/provider-probes`，并验证托管进程回收。供应商探测分别执行一次最小 Embedding 与聊天调用，只保留脱敏状态，因此会产生少量外部调用和可能的费用。任一能力未配置、鉴权失败、限流、超时、5xx、网络不可达或响应无效时，预检在三类评估前失败关闭。它不运行测试、评估或门禁，不写 `verification_latest`、`quality_gate_latest` 和评估报告；托管启动日志仍会更新。返回非零时先根据 `reasons`、能力状态、状态码和凭据来源修复环境，不应覆盖或重新解释上一份质量结论。

预检通过后执行完整验证：

```powershell
python scripts/verify_quality.py --manage-api --api-base http://127.0.0.1:8017 --api-key-file C:\secure\quality-api.key
```

托管模式只接受带显式端口的 `http://localhost`、`127.0.0.1` 或其他 loopback IP，不接受 HTTPS、远程主机、用户信息、路径前缀、查询和片段。目标端口必须空闲；脚本不会复用或终止未知监听进程。它启动自己拥有的 Uvicorn 子进程，等待 `/health`，再执行原验证流程，并在成功、失败或中断后回收 API。Windows 使用 `CTRL_BREAK_EVENT` 请求 Uvicorn 优雅关闭，POSIX 使用 `SIGTERM`；等待超时才强制 kill，结果记录 `shutdown_signal`、`forced` 和原始 `exit_code`。Windows 下 Uvicorn 完成 shutdown 后可能重放控制事件并返回非零进程码，应结合 `forced` 和启动日志中的 `Application shutdown complete` 判断，不能单看退出码。默认最长等待 60 秒，可用 `--api-start-timeout-seconds` 调整。

API 子进程继承当前环境，并自动把同一 `--api-base` 注入 `ANSWER_EVALUATION_API_BASE`。`ZHIPUAI_API_KEY`、`MIMO_API_KEY`、`API_KEYS` 等秘密不会进入进程参数或验证报告；错误摘要按已知秘密变量脱敏。启动日志写入 `data/audit/reports/managed_quality_api_latest.log`。启动失败会覆盖生成一份新的失败验证报告，不能沿用上一份成功证据。

关闭 API 鉴权的本地环境应显式声明无 Key，避免误用遗留兼容文件：

```powershell
python scripts/verify_quality.py --manage-api --api-base http://127.0.0.1:8017 --no-api-key
```

连接已经由部署系统启动的 API 时，省略 `--manage-api`，并显式指定同一个目标：

```powershell
python scripts/verify_quality.py --api-base http://127.0.0.1:8017 --api-key-file C:\secure\quality-api.key
```

验证器分别请求公开的 `/ready` 和受保护的 `/admin/status`。未就绪时报告列出 `reasons`；401/403 则单独报告凭据错误，两者都不会提交注定失败的后台任务。凭据优先级为 `QUALITY_API_KEY`、`--api-key-file`、`QUALITY_API_KEY_FILE`、兼容 `.runtime_api_key`，`--no-api-key` 会忽略全部来源。报告不保存 Key 值。

预检通过只代表本地资产、管理鉴权和两项外部能力在检查时刻可用，不代表 100 条常规检索、12 条结构化检索、24 条回答盲测或自动门禁通过。供应商能力失败是执行前置条件失败，不是模型内容质量失败。

常规、结构化与回答评估分别使用内置标识 `regular`、`structured`、`answer`。验证器和控制台不向 API 发送本机文件路径；服务端负责映射版本化评估资产，报告写入 `evaluation_set_id`、实际路径和哈希。完整验证还会生成 `verification_run_id`，三类报告必须来自该次运行；API 根据当前非敏感设置和关键实现计算 `runtime_config_hash`，客户端不能覆盖。回答级盲测由验证器直接请求同一目标的问答与图片接口，因此 `--api-base` 不会在后台退回默认端口。控制台发起回答盲测时则使用服务端 `ANSWER_EVALUATION_API_BASE`，自定义 API 监听地址的部署必须同步设置该变量。

评估集维护在后台的“评估集管理”页面完成。首屏是评估集目录，分别展示 `regular`、`structured`、`answer` 的用途、用例数量、当前版本和未发布修改状态；打开其中一项后进入单集工作区。工作区的“用例”页签用于搜索、筛选、查看和编辑用例，默认使用与评估集契约对应的结构化表单，只有处理扩展字段或诊断格式时才切换“高级 JSON”；“版本记录”页签用于查看历史版本和执行受控恢复；“发布”页签集中处理修改内容、结构检查和发布确认。点击“开始编辑”后，系统内部会创建一个不影响当前正式版本的工作副本；页面将其统一称为“未发布修改”，不要求维护者理解内部草稿模型。发布不会覆盖历史版本，也不会立即让旧评估报告变成新证据；发布或恢复历史版本会写入 `data/evaluation_sets/quality_refresh_queue.jsonl`，完成后应通过“前往质量验证”进入独立的质量验证中心重新运行受影响评估。质量验证中心的“评估集浏览器”仍是只读视图，不能绕过编辑、检查和发布流程。首期为单机单维护者能力，不支持上传任意 JSONL、PDF、路径或 URL。

质量重跑和报告比较按以下顺序执行：

1. 在质量验证中心查看“评估集变更待重跑”，确认评估集、目标修订和缺失报告类型；不要把旧报告手工复制为新证据。
2. 点击“运行受影响评估”或分别运行常规、结构化和回答级评估；任务完成后刷新质量门禁，确认报告修订和哈希与当前发布修订一致。
3. 在“质量运行比较”选择两个完整运行，比较评估集身份、数据版本、配置指纹、指标和失败用例变化；不完整或损坏的运行不会出现在列表中。
4. 若结果仍未通过，保留失败报告和审计事件，先处理数据、检索、解析器或外部服务问题，再创建新的质量运行。

退出码为非零时不得把当前活动版本视为可发布。候选激活门禁通过只证明运行时一致性和检索评估通过，不等于完整发布门禁。评估报告包含知识库数据版本与评估集哈希；重建知识库、修改任一评估集或报告生成时间超过 7 天后，旧报告会自动判定为过期。回答级门禁要求总体通过率不低于90%，规范依据、证据归属、截图来源、截图HTTP与拒答关键检查必须全部通过。

每次完整验证会先写入 `data/audit/reports/runs/<verification_run_id>/`，其中包含常规检索、结构化检索、回答盲测、质量门禁和总验证的 JSON/Markdown。只有十个产物齐全、JSON 可读、运行身份一致且清单哈希完成后，才更新 `quality_run_latest.json`；`*_latest` 是兼容副本，不是新代码的权威入口。仅修复不改变运行语料的 manifest 漂移时，必须使用 `scripts/publish_equivalent_quality_evidence.py`，它会校验候选门禁和全量语料摘要后发布带 `evidence_mode=inherited_runtime_corpus_equivalence` 的新运行，不得直接复制或手改旧指针。检查运行时应先查看指针的 `status=complete`、`verification_run_id`、`passed` 和对应 `manifest.json`。指针损坏、清单哈希不符或任一产物漂移都按阻断处理。

托管 API 模式由子进程准备报告，父进程在 API 回收完成后才发布指针。若命令中断、交接文件缺失或最终发布失败，上一份完整指针保持不变；未发布的运行目录应保留用于诊断。清单已经生成的运行目录不可编辑，只能在产物和参数未变化时重试发布，或开始新的验证运行。

每次有意保留新的质量执行结果后，运行以下命令同步脱敏证据状态：

```powershell
python scripts/snapshot_quality_evidence.py --write
python scripts/snapshot_quality_evidence.py
```

`--write` 必须在持有本地完整质量运行的受控环境运行。新契约环境从 `data/audit/reports/quality_run_latest.json` 校验清单和全部产物后，读取同一运行的验证、门禁和三类评估报告；仅当指针不存在时兼容旧版 `*_latest.json`。快照同时记录评估集的跨平台规范化哈希、原始字节哈希，以及三类报告实际绑定的评估集哈希。报告绑定哈希与当前评估集不一致时，状态为 `stale`；无法取得绑定哈希时为 `unverified`；只有报告通过且三类绑定均匹配才是 `passed`。旧快照不会因为重新生成快照而被伪装成新评估结果。快照按“`docs/quality/质量证据历史/` 归档 → `质量证据历史索引.json` → `质量证据状态.json`”的顺序原子提交，相同输入重复执行不会增加历史文件；新的失败或过期快照同样必须保留。

第二条命令验证归档结构与文件名指纹、重复内容、确定性索引、当前快照已归档、三份评估集和系统卡；源报告存在时再核对其哈希，干净 CI 检出则不要求提交被忽略的审计目录。历史文件和索引不得手工修改；需要纠错时保留旧证据并从新的受控报告重新生成。任何失败快照都必须在系统卡中明确标记为不可发布，不能保留旧的通过文字。Git 历史只提供内部追溯，不替代签名、可信时间戳或外部证据保全。

质量运行目录不自动删除。先只读查看分类、保护原因和候选状态：

```powershell
python scripts/manage_quality_runs.py plan
python scripts/manage_quality_runs.py execute <plan_id> --confirm
```

默认保护最新指针、当前及历史脱敏快照引用、最近 10 个封存运行和 24 小时内变化的运行；封存运行 90 天、未封存运行 7 天后才可能进入计划。`plan` 只生成 15 分钟有效的持久化计划，没有删除副作用。执行前会持有质量报告存储锁，重新验证保护集、目录内容指纹和候选资格；任何漂移都要求重新生成计划。计划、执行报告和事件位于 `data/audit/quality_run_retention/`。不得直接删除 `runs/` 子目录，也不得用清理工具替代 `DATA_DIR` 备份。详细格式见[质量运行证据保留格式规范](../reference/质量运行证据保留格式规范.md)。

任务 `succeeded` 表示评估用例完整执行，不表示质量已经通过。完整执行后出现检索失败用例或回答断言失败，由报告和质量门禁判定；检索服务未就绪、目标不可达、响应无效或回答请求未完成属于执行失败，任务状态为 `failed`，同时保留报告路径和明确错误。排障时应先修复执行失败，再解读命中率或通过率。

`package-export` 会再次实时计算门禁并默认阻断失败导出。只有受控排障等例外场景才能同时填写 `--quality-waiver-actor` 与 `--quality-waiver-reason`；系统会把失败项、责任人和原因写入包清单及 `data/audit/package_exports/`。豁免只绕过自动质量条件，不绕过来源权利、人工校对、鉴权或回退要求。

本机验证通过带 API Key 的 `127.0.0.1` 管理接口运行，不占用公网请求限流额度。带有 `Forwarded` 或 `X-Forwarded-For` 的 Cloudflare 请求仍执行限流。

任务状态中：

- “未解决失败”表示某类任务最近一次结果仍然失败；
- “历史失败”只用于审计，若同类任务后来成功则不阻断门禁；
- 对于没有同类成功任务但已经完成核对的历史失败，在构建任务详情中使用“记录失败处置”：`acknowledged` 需要填写核对说明，`superseded` 还必须关联一个 `succeeded` 任务。系统只追加处置对象和 `JOB_FAILURE_RESOLVED` 日志，不修改原始失败状态；处置记录缺少状态、说明或时间时仍按未解决处理；
- `queued`/`running` 按 `progress_at` 计算无进展时间；旧记录回退到 `started_at`/`created_at`。默认超过 2 小时会进入“疑似卡滞”并阻断质量门禁；
- 心跳表示执行器仍在维护任务，进度时间表示步骤发生变化。仍有心跳但无进度通常应先检查外部模型、解析器或大文件步骤；心跳同时过期则检查 API 进程和任务日志；
- 构建任务详情可对当前 API 进程持有的 `rebuild`/`source_rebuild` 发起“取消构建任务”。排队任务会立即取消；运行任务在协作式检查点停止，MinerU CLI 被中断时会尝试回收其整个子进程树。界面出现“取消请求已提交”后，等待任务最终变为“已取消”，不要重复提交；非构建任务、由其他 API 进程执行的任务和版本原子激活阶段不支持取消。取消不会回滚已完成的文件处理，也不会关闭 API 服务；
- 构建任务详情中的“当前进度”优先看阶段消息和当前文档，再看页面、Chunk、Embedding 计数；`parser_output` 是解析器最近一行输出，不等于完整日志。没有真实总量时不显示百分比，不能根据耗时推断完成度；需要完整上下文时查看同名 `.jsonl` 日志；
- `PROCESS_RESTARTED` 表示 API 重启后安全收口的中断任务。系统不自动续跑；核对候选目录、输出和外部副作用后，再显式提交新任务；
- 不要手工把持久任务 JSON 改成成功，也不要因为中断任务已失败就绕过版本、回退点或最短保护期规则。

## 版本保留与清理

1. 在控制台“版本管理”查看活动版本、门禁状态、占用和保护原因；不直接在文件系统删除 `data/db_versions` 子目录。
2. 对事故证据、长期对照样本或指定回退点开启“人工固定”。损坏的固定标记按受保护处理，必须先修复标记才能清理。
3. 点击“生成清理计划”。计划只包含当时未受保护且满足期限或磁盘水位条件的版本，并保存目录指纹和策略快照。
4. 核对版本、原因和预计释放空间后确认执行。后台任务会再次读取活动指针、运行任务、固定状态和指纹；变化项自动跳过。
5. 在构建任务查看执行日志，在 `data/audit/version_retention/` 查看计划、执行报告和 JSONL 事件。`partial_failed` 或后台任务失败必须处理后再生成新计划。

默认策略保留活动版本、2 个近期回滚版本和 24 小时内变化的版本；成功版本 30 天、失败或不完整版本 7 天后才可能按期限进入计划。版本总占用超过 20 GiB 时尝试回收到 16 GiB，但不会突破任何保护条件。调整策略后旧计划自动失效。

## 内部研究审计

当前扫描来源按 B 级登记，只允许项目成员范围内的内部研究和封闭验证。需要确认本地活动数据可以继续受控使用时，运行：

```powershell
python scripts/audit_release_readiness.py --profile internal-research
```

该 profile 必须通过质量证据、运行 manifest 和来源台账的内部用途检查；通过只表示内部研究可用，不要求真实用户试用，也不授予截图、摘录、表格、知识包、问答或 API 的对外传播权。对外发布仍必须运行默认 `external` profile，并完成来源权利、封闭试用和交付边界审计。

默认外部审计返回非零时，先查看 JSON 中 `checks[id=source_release].items`，按来源登记台账逐项处理取得凭证、权利复核和仓库存储处置；使用 `--markdown-output` 可生成适合人工阅读的“来源资格明细”章节。该明细只解释阻断原因，不降低来源资格门槛，也不替代法律或权利判断。

同时按 `checks[].remediation` 的责任角色、整改动作和验证条件安排处理。行动建议只作为治理提示，不自动改台账、不生成试用证据，也不替代 D-001/D-002 决策；完成后必须重新运行原校验器和发布审计。

当来源、试用和决策证据分散在受限目录时，使用证据包索引统一收口：

```powershell
python scripts/create_release_evidence_manifest.py --output <受限目录>\release-evidence.json
python scripts/validate_release_evidence_manifest.py --manifest <受限目录>\release-evidence.json --markdown-output <受限目录>\release-evidence.md
python scripts/validate_release_evidence_manifest.py --manifest <受限目录>\release-evidence.json --require-ready
python scripts/audit_release_readiness.py --evidence-manifest <受限目录>\release-evidence.json
```

索引只保存脱敏引用、责任人、日期和文件哈希，必须放在受限目录且不得提交 Git。`--require-ready` 通过后仍需分别通过来源资格、试用记录、交付决策和质量门禁；不要把索引状态直接改成 `ready` 来替代真实证据。

## 外部依赖优化

- 学习型 reranker：已实现默认关闭的智谱 HTTP 提供方、扩展候选池、基线/模型秩融合和失败降级。启用前运行 `python -m src.evaluation compare-rerank --json-output <路径> --markdown-output <路径>`，并在同一数据版本上复核 100 条检索指标、回答盲测、时延、费用和 `rerank_fallback_total`；没有真实对照证据时保持关闭。
- 真实精排对照优先使用 `python scripts/run_rerank_evidence.py --api-key-file <受限 Key 文件>`。该入口强制启用智谱精排，只在对照调用期间注入 Key，返回或失败后恢复原环境，并将对照结果写入独立的 `rerank_comparison_latest.json/md`；它不会覆盖 `quality_run_latest.json`，也不能单独关闭 I-034。
- 需要同时完成回答盲测时使用 `python scripts/run_rerank_quality_evidence.py --zhipu-key-file <智谱 Key 文件> --api-key-file <目标 API Key 文件> --mimo-key-file <Mimo Key 文件>`。该入口会在 loopback 临时启动启用精排的 API，写入 `rerank_comparison_latest.json/md` 与 `rerank_answer_latest.json/md`，结束后回收 API；两份报告均独立于 `quality_run_latest.json`。`--api-key-file` 同时作为客户端凭据和临时 API 子进程的 `API_KEYS`，只进入子进程，不修改当前终端环境；省略时临时 API 继承当前环境的鉴权配置。
- OCR/版面引擎升级：属于独立基础设施工作，需要模型、算力和部署环境，不在当前自动化闭环内。
- 新规范接入后应扩展评估集，不能仅依赖现有规范的历史通过率。
