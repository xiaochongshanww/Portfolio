## 1. 适用范围

本文档覆盖宿主机和 Docker Compose 运行方式。Dockerfile 使用多阶段构建生成并复制 `frontend/dist`；GitHub Actions 已在 Linux Runner 完成镜像构建、API 容器健康检查、静态控制台检查，以及使用受保护 API 连接的真实 OpenWebUI v0.9.5 模型发现。该证据验证仓库声明的容器拓扑，不代表任意生产网络、代理或身份系统已经通过验收。

## 2. 前置条件

- Python 3.11 运行环境。
- Node.js 22 与 npm 10.9.8，用于可复现地构建 Vue 控制台。版本契约同时记录在 `frontend/package.json`，`frontend/.npmrc` 会拒绝不匹配的 npm 版本；不得用 npm 11 重写锁文件。
- 使用容器方式时需要 Docker Engine 与 Docker Compose v2。
- 以下两种数据准备方式任选其一：在构建环境持有 PDF、MinerU（或显式选择 PyMuPDF）和 Embedding 能力并完成重建；或在轻量运行环境导入已验证的运行知识包。导入运行包不需要 MinerU。
- `ZHIPUAI_API_KEY` 和 `MIMO_API_KEY`。不将真实密钥提交到 Git。
- 只有开发和自动化测试环境安装 `requirements-dev.txt`；提交 Python 变更前执行 `python -m ruff check src scripts tests` 和 `python -m ruff format --check src scripts tests`。轻量运行与知识生产环境不需要 Ruff。

## 3. 本地启动

```powershell
Copy-Item .env.example .env
# 在 .env 中填写 ZHIPUAI_API_KEY、MIMO_API_KEY 和生产所需的 API_KEYS。

python -m pip install --require-hashes -r requirements-runtime.txt
python -m pip check
Push-Location frontend
npm install --global npm@10.9.8
npm ci
npm run build
Pop-Location

python -m src.app.core.config
python -m src.doctor --profile runtime
python -m uvicorn src.app.main:app --host 127.0.0.1 --port 8000
```

只有需要从 PDF 重新解析和构建知识库的环境才安装精确锁定的 `requirements-parser.txt`。安装后先执行 `python -m pip check`，再执行 `python -m src.pipeline parser-status`，确认依赖图无冲突且外部实现为 `magic-pdf 1.3.12`、`verified=true` 后再提交重建任务。API、控制台和已验证运行知识包的部署只使用 `requirements-runtime.txt`；自动化测试使用 `requirements-dev.txt`。

`python -m src.doctor` 将解释器、精确锁直接依赖、真实应用配置、模型凭据、前端入口、活动 manifest、数据库和来源元数据收敛为一次只读检查。PDF 知识生产机使用 `python -m src.doctor --profile build`，额外检查输入 PDF、生产目录和 MinerU 严格兼容状态，但不误要求已经存在运行知识库或回答模型凭据。默认文本适合人工排障；自动化使用 `--format json`。必需检查失败时退出码为 1，警告本身不阻断。

自检不创建缺失目录、不安装依赖、不修改资产、不启动 API，也不调用模型。通过后再启动服务并检查 `/ready`；`/ready` 验证实际检索初始化，发布质量门禁验证检索与回答质量，三者不能相互替代。

运行锁、开发锁和知识生产锁同时固定版本与分发包哈希。直接依赖只在 `.in` 文件维护，`dependency-lock.json` 固定 Python 版本、`uv` 版本和 `exclude_newer` 时间截点。升级时先更新直接依赖和时间截点，再用固定工具执行：

```powershell
python -m pip install -r requirements-tools.txt
python scripts\lock_dependencies.py --write
python scripts\lock_dependencies.py --check
```

复制或修改环境配置前，先验证仓库示例本身：

```powershell
python scripts\validate_configuration_example.py
docker compose --env-file .env.example config --quiet
```

第一条命令验证 dotenv 格式、重复键、空敏感占位和应用启动配置；第二条命令验证 Compose 渲染。两者通过只表示示例结构有效，不表示模型 Key、内容授权、知识库就绪或目标部署安全配置已经完成。实际 `.env` 必须独立创建并由秘密管理方式填充，不在 `.env.example` 中保存真实值。

禁止手工修补 `.txt` 锁文件，也禁止在生产安装中去掉 `--require-hashes`。CI 会在 Ubuntu/Windows 分别安装开发锁、执行 `pip check` 并运行全量测试；产包环境也在处理知识包前检查运行依赖图。Docker 构建在 Python builder 中验证 Linux 运行依赖图，再把站点包复制到不含 pip 的最终镜像。

校验：

```powershell
Invoke-WebRequest http://127.0.0.1:8000/health
Invoke-WebRequest http://127.0.0.1:8000/ready
```

根路径会重定向到 `/static/index.html`。若未构建 `frontend/dist`，控制台不会被挂载。

控制台不会根据浏览器是否保存 API Key 猜测服务端配置。页面首次加载和手工刷新会先请求 `/admin/status`：返回 2xx 时直接进入并加载各工作区；返回 401 时才显示 API Key 验证界面；网络错误或 5xx 显示“后端暂时不可用”并允许重试。候选 Key 只有在 `/admin/status` 验证成功后才写入当前浏览器的 `localStorage`，验证失败不会覆盖此前保存的值。该机制只是客户端握手，公网部署仍必须按第 5 节启用鉴权。

## 4. Docker Compose 启动

Docker 镜像会在独立 Node 22 构建阶段固定 npm 10.9.8，再执行 `npm ci` 和生产构建；CI 使用相同组合。最终镜像只复制 `frontend/dist`，不携带 Node.js 工具链。运行时镜像还包含评估集、规范元数据和动态 PDF 页面渲染所需的 PyMuPDF。API 与 preflight 复用同一 `structural-spec-kb` 镜像；`STRUCTURAL_SPEC_KB_IMAGE_TAG` 只用于 Compose 选择已构建标签，默认 `local`。

Compose 文件显式使用项目名 `structural-spec-kb`，避免中文目录名无法自动转换为合法 Compose 项目名。
服务级 `.env` 声明为可选，因此 CI 和代码审查环境可以在没有私密配置文件时执行 `docker compose config -q`；真正启动可用服务前仍必须从示例创建 `.env`，并通过配置预检和 `/ready` 检查。

```powershell
Copy-Item .env.example .env
# 填写模型密钥；启用鉴权时同时配置 API_KEYS、OPENWEBUI_API_KEY 和 ASSET_SIGNING_KEY。
python -m src.app.core.config
python scripts/validate_container_images.py
docker compose config -q
python scripts/pull_compose_images.py open-webui
docker compose up --build --pull never -d
docker compose ps
Invoke-WebRequest http://127.0.0.1:8000/health
Invoke-WebRequest http://127.0.0.1:8000/static/index.html
```

`pull_compose_images.py` 仅依赖 Python 标准库，并调用本机 Docker Compose。它默认最多尝试 5 次、每次最多等待 600 秒，仅对仓库限流、网络/TLS 超时、连接中断、临时 DNS 和临时网关错误执行有上限的指数退避；单次超时会终止该次 Compose 命令并参与有限重试，耗尽后返回 124。镜像不存在、仓库鉴权失败、服务名错误及未知错误立即保留原退出码失败。诊断输出会脱敏凭据。默认 `--policy missing` 可复用本地缓存；需要主动刷新同一标签时显式增加 `--policy always`。可通过 `--attempt-timeout` 调整单次上限，但外层部署窗口仍应设置独立总超时。前置拉取成功后必须使用 `--pull never` 启动，避免启动阶段再次隐式访问镜像仓库。

Compose 显式设置 `DATA_DIR=/app/data`，将整个 `./data` 挂载到该目录，并将旧库回退目录 `./db` 和日志目录 `./logs` 分别持久化；Open WebUI 内部状态使用命名卷。这样可覆盖 manifest、活动数据库指针、数据库版本、来源策略、结构化表、校对记录和评估证据。该挂载也会把 `data/raw` 提供给 API 进程；页面是否允许展示由 `data/metadata/specs.json` 控制，但来源策略不替代内容授权审核。

Open WebUI 使用 `http://api:8000/v1` 作为唯一 OpenAI-compatible 基址。若 `API_AUTH_ENABLED=true`，`OPENWEBUI_API_KEY` 必须等于 `API_KEYS` 中的一个有效 Key。Compose 通过复数变量 `OPENAI_API_BASE_URLS`/`OPENAI_API_KEYS` 声明连接，并固定 `ENABLE_PERSISTENT_CONFIG=false`：环境变量是每次启动的连接事实来源，旧数据卷中的连接配置不会覆盖它。用户、聊天和文件仍保存在命名卷中，但管理界面修改的 ConfigVar 不保证重启后保留，持久变更应写回 Compose 配置或 `.env`。

### 4.1 OpenWebUI 启动闭环

`openwebui-preflight` 是一次性服务，不调用外部模型。它先校验 Key 关系，再通过容器网络验证 API 健康、模型发现、匿名/带 Key 管理请求以及 malformed chat 请求的鉴权顺序。`open-webui` 同时等待 API 健康和 preflight 退出码 0；Key 缺失、错配、目标鉴权状态不符或 API 不可达都会阻止 OpenWebUI 启动。

```powershell
python scripts/pull_compose_images.py open-webui
docker compose up --build --pull never --detach open-webui
docker compose ps --all
docker compose logs --no-color openwebui-preflight
Invoke-WebRequest http://127.0.0.1:3000/health
```

`openwebui-preflight` 显示 `Exited (0)` 是成功的预期终态，不是崩溃。其最后一条 JSON 应包含 `"ok": true`，且不得出现任何 Key 原值。API 已运行时可以单独复检：

```powershell
docker compose run --rm openwebui-preflight
```

鉴权关闭时无需设置 `OPENWEBUI_API_KEY`，Compose 会给 OpenWebUI 传入无权限意义的占位值；探针仍会确认目标 API 确实处于未鉴权状态。标准部署保持 `OPENWEBUI_AUTH=true`。`OPENWEBUI_AUTH=false` 只用于一次性无人值守联调，不得作为公网部署默认值。

### 4.2 连接 Key 轮换与旧配置迁移

连接 Key 采用两阶段轮换，避免 API 和 OpenWebUI 在切换过程中失配：

1. 在受控密钥源中生成新 Key；把新旧 Key 同时放入 `API_KEYS`，将 `OPENWEBUI_API_KEY` 改为新 Key。
2. 重建 API、preflight 和 OpenWebUI，确认 preflight 退出码 0、OpenWebUI `/health` 成功且模型列表包含 `MIMO_MODEL`。
3. 从 `API_KEYS` 删除旧 Key，再次重建三个服务并重复验证。
4. 在轮换记录中保存时间、责任人、目标环境和探针结果，只记录 Key 指纹或密钥系统版本，不记录原值。

```powershell
python scripts/pull_compose_images.py open-webui
docker compose up --build --pull never --detach --force-recreate api openwebui-preflight open-webui
docker compose ps --all
docker compose logs --no-color openwebui-preflight
```

从旧 Compose 升级时不需要删除 `open-webui-data` 卷。`ENABLE_PERSISTENT_CONFIG=false` 会让旧连接停止生效；先把仍需保留的管理界面 ConfigVar 显式迁移为环境变量，再重建服务。删除卷会同时删除账户、聊天、上传文件等状态，只能作为已有独立备份且确实要全新初始化时的破坏性操作。

### 4.3 外部镜像身份与更新

Dockerfile frontend、Node builder、Python builder/runtime 和 OpenWebUI 使用“可读标签 + 多架构 `sha256` 摘要”。摘要确保同一提交解析到已声明 OCI image index；本地 `structural-spec-kb:*` 由当前源码构建，可在 Compose 服务间复用，不作为外部镜像处理。

日常启动前只执行确定性校验，不访问 registry：

```powershell
python scripts/validate_container_images.py
```

每周定时任务 `Container Supply Chain Drift` 和人工维护窗口执行远程比对：

```powershell
python scripts/validate_container_images.py --check-remote
```

返回 `REMOTE_DIGEST_DRIFT` 表示标签当前摘要与仓库固定值不同，不表示新镜像已经可信或应自动上线；`REMOTE_QUERY_*` 表示查询基础设施失败，不能当作无漂移。更新流程为：

1. 读取 Dependabot PR 或漂移报告，确认目标标签、上游发行说明、来源、许可和平台清单。
2. 使用 `docker buildx imagetools inspect <tag> --format '{{json .Manifest}}'` 获取多架构 index digest；同时更新标签和摘要，禁止只删除摘要绕过校验。
3. 运行离线校验和 `--check-remote`，确认 Dockerfile 的 Python builder/runtime 完全一致，Compose 渲染后仍保留摘要。
4. 构建应用镜像，按本节执行显式外部拉取、`--pull never` 启动、preflight、健康和模型发现验证。
5. 通过完整 Windows/Linux、前端、容器、OpenWebUI 和知识包矩阵后再合并，不自动合并 Dependabot 变更。

摘要固定不提供漏洞扫描、签名验证或上游信任。发现安全公告时不能等待每周漂移任务；应立即按同一流程更新，并在发布记录中保存旧/新标签、摘要、审阅依据和 CI 链接。

### 4.4 运行镜像 SBOM 与漏洞门禁

本地和普通提交先执行不访问外部服务的策略校验：

```powershell
python scripts/validate_container_security.py
```

每周供应链任务额外检查固定 Trivy 是否仍为上游最新不可变发行版，以及已审阅 Linux amd64 归档摘要是否一致：

```powershell
python scripts/validate_container_security.py --check-remote
```

主 CI 扫描 `structural-spec-kb:ci` 最终运行镜像，上传 `container-security-evidence` artifact，其中包含 scanner version、SPDX JSON SBOM 和未应用例外的完整漏洞 JSON，保留 14 天。门禁只阻断具有修复版本的 HIGH/CRITICAL OS 与语言依赖漏洞；未修复项仍须在完整报告中审阅。绿色结果只代表当次漏洞数据库和策略下通过，不等同于零漏洞、许可证合规或镜像签名。

优先通过升级基础镜像或依赖消除发现。确需例外时，只能在 `.trivyignore.yaml` 的 `vulnerabilities` 中增加单项记录，使用 `paths` 或 `purls` 限定范围，设置不超过 90 天的 `expired_at`，并在 `statement` 中写明 `owner=`、`tracking=` 和 `reason=`。修改后重新运行策略校验；全局、永久、过期、重复或缺治理信息的例外会失败关闭。上游 YAML 例外格式仍属实验能力，因此仓库校验器有意冻结为当前最小子集，升级 Trivy 时必须复核格式兼容性。

### 4.5 Docker 构建上下文

`.dockerignore` 以 `**` 默认排除整个工作目录，只放行 Dockerfile 实际使用的后端 `src/`、前端生产源码与配置、`requirements-runtime.txt`、`data/evaluation/` 和 `data/metadata/`。Dockerfile 不再复制整个 `frontend/`，而是逐项复制 `.npmrc`、包清单、Vite/TypeScript 配置、入口、`public/` 与 `src/`；`node_modules`、测试配置、OpenAPI 生成输入、前端构建产物和任意顶层环境文件均不进入 builder。缓存和 Python 字节码在允许目录内也会再次排除。本机 `.tools`、`db`、其余 `data`、`.runtime_*`、日志、测试和文档不进入上下文；该边界不依赖它们是否被 Git 忽略。

构建前执行确定性校验：

```powershell
python scripts/validate_docker_context.py
```

校验器同时解析 Dockerfile 的本地 `COPY` 来源。新增或删除来源时，先确认最终镜像确实需要，再同步更新 `.dockerignore`、校验器允许集、测试与本文；出现 `UNREVIEWED_ALLOW_RULE` 或 `UNREVIEWED_COPY_SOURCE` 时不得用 `!**`、`!data/**` 等宽泛规则绕过。该门禁降低误发送和构建开销，但远程 BuildKit 仍必须配置受控访问、TLS 和独立秘密管理。

### 4.6 非 root 运行身份与绑定卷

API 镜像把依赖安装到 `/opt/venv`，在复制前执行 `pip check` 并移除 venv 安装工具；最终阶段继续移除系统 pip、setuptools 和 wheel。所有源码和依赖复制完成后，进程切换为专用 `app` 用户。镜像默认 UID/GID 为 `10001:10001`；Compose 默认构建为 `1000:1000`，并允许通过 `.env` 的 `APP_UID`、`APP_GID` 对齐 Linux 宿主机绑定卷。

Linux 首次构建或更换运行账户时执行：

```bash
printf 'APP_UID=%s\nAPP_GID=%s\n' "$(id -u)" "$(id -g)"
# 将上述值写入已有 .env 对应项，然后重建
docker compose build --no-cache api
docker compose up --pull never --detach api
docker exec rag-api id
docker exec rag-api sh -c 'test "$(id -u)" != 0 && test -w /app/data && test -w /app/db && test -w /app/logs'
```

若现有 `data/`、`db/` 或 `logs/` 来自旧 root 容器，应在维护窗口停止服务并由宿主机管理员把所有权迁移到目标 UID/GID，再启动新镜像。不要把容器改回 root，也不要使用全局可写权限；生产编排平台可改用具备等价所有权的持久卷或 `fsGroup` 策略。Docker Desktop 的文件共享层通常不使用 Linux 宿主机所有权，可保持示例默认值，但仍应执行 `docker exec rag-api id` 与写权限探针。

## 5. 生产配置最低要求

- 设置 `API_AUTH_ENABLED=true` 和强随机 `API_KEYS`。
- 为 Open WebUI 设置单独的 `OPENWEBUI_API_KEY`，并将同一值加入 `API_KEYS`。
- 设置独立、随机且至少 32 字符的 `ASSET_SIGNING_KEY`；按客户端阅读时间设置 `ASSET_URL_TTL_SECONDS`，默认 3600 秒。
- 将 `CORS_ORIGINS` 限制为明确的控制台域名。
- 将 `PUBLIC_ASSET_BASE_URL` 配置为同一个 FastAPI 服务的外部资源前缀；受保护签名必须由该服务验证，不能把资源路径改指向无策略的静态主机。
- 在 `data/metadata/specs.json` 为每份来源显式设置 `image_access` 和 `page_image_access`。网上收集的扫描件默认使用 `authenticated`，未确认展示许可的来源使用 `disabled`；只有确认可公开的资料使用 `public`。
- 通过反向代理终止 TLS；不要把开发端口直接暴露到公网。
- 生产运行必须把 `DATA_DIR` 放在受备份保护的持久卷；只有确需拆分旧库回退或图片资产时才单独设置 `DB_DIR`、`IMG_DIR`。
- 使用 `LOG_FORMAT=json` 输出可采集的单行结构化日志，并在日志平台按 `request_id`、`event`、`job_id`、`status` 和 `error_code` 建立索引。
- 当前后台任务所有权只支持单 API 进程、单工作线程；不要设置 Uvicorn `--workers`、`WEB_CONCURRENCY>1` 或同时挂载同一 `data/jobs` 的多个 API 副本。扩容前必须先替换为跨进程任务队列与租约协议。
- 检查模型供应商的地区、数据保留和密钥管理约束。

### 5.1 运行观测与告警

API 为每个请求生成或规范化 `X-Request-ID`，在响应、结构化日志和由该请求创建的后台任务日志中保持一致。生产日志应写入标准输出并由容器平台或日志代理采集，不依赖本地临时日志文件作为唯一证据。

最小告警建议：

1. `/health` 连续失败：进程或网络故障，立即告警。
2. `/ready` 连续返回 503：按 `reasons` 区分知识库、密钥、BM25、manifest 或集合数量问题；停止接收问答流量，但保留控制台用于诊断。
3. `/metrics` 中 5xx 状态持续增长、`errors_by_code` 异常增加或请求最大/平均耗时显著抬升：保留关联 `request_id` 并检查对应事件日志。
4. 后台任务出现“疑似卡滞”、心跳过期、`PROCESS_RESTARTED` 或 `job_failed`：通过 `/admin/jobs/{job_id}` 和 `/logs` 核对诊断、最近进度、创建请求及候选产物。卡滞标记不会终止线程，中断任务不会自动重跑。

`/metrics` 是单进程、重启清零的运行快照。多 worker 或多副本部署不能直接累加这些值，应由外部采集系统按实例保存和聚合。日志禁止写入 API Key、完整用户问题、完整模型回答、受限规范原文和客户端 IP；当前 RAG 事件只记录查询字符数、候选数量和上下文规模。

## 6. 运行知识包部署

知识资产维护者在已完成校对和质量验证的构建环境导出：

```powershell
python scripts/verify_quality.py --manage-api --api-base http://127.0.0.1:8017

# 默认不包含原始 PDF
python -m src.pipeline package-export --output dist\knowledge-runtime.zip

# 只在来源权利和目标用途允许时显式包含原始 PDF
python -m src.pipeline package-export --output dist\knowledge-runtime-with-pdf.zip --include-source-pdfs
```

导出会实时复核当前数据版本、评估集哈希和报告年龄，默认有效期为 168 小时。门禁失败时不会生成知识包，并在 `data/audit/package_exports/` 留下阻断记录。仅在已有独立风险批准的受控例外中使用：

活动 manifest 中的测试夹具（`status=test`）不会进入生产运行包；若存在，导出会失败关闭，必须先生成不含测试夹具的活动知识版本。

若仅需修复活动 manifest 中的测试来源漂移，且活动 Chroma 不变，可使用候选门禁执行等价语料修复：

```powershell
python scripts/repair_runtime_manifest.py `
  --candidate-dir data/db_versions/runtime-manifest-repair-equivalent `
  --reuse-equivalent-evidence `
  --activate
python scripts/validate_runtime_manifest.py
python scripts/validate_source_register.py
python scripts/publish_equivalent_quality_evidence.py
python scripts/snapshot_quality_evidence.py --write
```

修复命令及其两个校验命令只在候选数据库与活动数据库逐条 ID、文本和元数据摘要一致时允许继承既有评估证据；`publish_equivalent_quality_evidence.py` 会将继承证据发布为新的不可变质量运行，最后用 `snapshot_quality_evidence.py --write` 同步脱敏快照。它不替代 MinerU 重建、重新评估、来源授权复核或真实试用。激活后必须重启 API，因当前运行进程不会热重载活动数据库。

```powershell
python -m src.pipeline package-export `
  --output dist\knowledge-runtime.zip `
  --quality-waiver-actor "release-owner" `
  --quality-waiver-reason "受控排障交付，禁止对外发布"
```

责任人和原因会进入 v2 及以上版本的包清单与审计记录。不得用豁免代替重新评估或内容授权判断。

目标环境应先做只读校验，再导入 `DATA_DIR`。以下示例使用默认项目 `data/`：

```powershell
python -m src.pipeline package-validate --package dist\knowledge-runtime.zip
python -m src.pipeline package-probe --package dist\knowledge-runtime.zip
python -m src.pipeline package-import --package dist\knowledge-runtime.zip
python -m uvicorn src.app.main:app --host 127.0.0.1 --port 8000
```

`package-validate` 只做静态格式、哈希和兼容性检查。`package-probe` 会在临时目录隔离导入，并由子进程真实打开 Chroma、核对集合数量和样本可读性；它不改变当前项目数据。只有两项都通过后才执行正式导入。

正式导入会把数据库安装为 `$DATA_DIR/db_versions/import-<package_id>/`，复制包内结构化表、图片和来源策略，并在最后更新 `$DATA_DIR/active_db.json` 与 `$DATA_DIR/manifest.json`。活动指针使用运行根相对路径，允许同一数据根在 Windows、Linux 和容器之间迁移；读取端仍兼容旧版 Windows/Posix 绝对路径。API 已运行时必须在导入后重启；当前命令不会热重载正在运行的进程。

使用自定义目录时，两条命令必须显式使用同一位置：

```powershell
$env:DATA_DIR = "D:\structural-kb\data"
python -m src.pipeline package-import --package dist\knowledge-runtime.zip --data-dir $env:DATA_DIR
python -m uvicorn src.app.main:app --host 127.0.0.1 --port 8000
```

操作约束：

1. 同一版本已安装或同名资产内容不同时，导入默认失败，不覆盖现有数据。
2. `--replace` 会覆盖冲突目标，只能在维护窗口、保留上一版完整知识包并确认新包来源后使用。
3. `--no-activate` 只安装独立数据库版本，不更新活动指针、根 manifest 或共享结构化表、图片和来源策略；预检仍应优先使用隔离的 `package-probe`。
4. `--data-dir` 主要用于预安装、测试或数据目录迁移；API 只读取启动前设置的 `DATA_DIR`，两者不一致时不会自动发现或切换。
5. 原始 PDF 默认不在包内；此时动态 `/page-images/*` 不可用，但已有解析图片仍可引用，纯文本问答不受影响。
6. 校验通过证明包未损坏，不证明内容获得传播、展示或商业使用授权。
7. 当前受控兼容矩阵仅覆盖 CPython 3.11、Chroma 1.5.9、x86_64 Windows/Linux；矩阵外环境必须重新验证，不得跳过探针。

### 6.1 受控升级与回退

当前运行时不承诺热重载或零停机。升级与回退必须使用完整知识包并进入维护窗口；不得手工修改 `active_db.json`，也不得只复制 Chroma 目录。发布前至少保留当前活动包和待部署包，并记录二者的 `package_id`、`data_version_hash` 与 SHA-256：

```powershell
Get-FileHash -Algorithm SHA256 dist\knowledge-runtime-current.zip
Get-FileHash -Algorithm SHA256 dist\knowledge-runtime-next.zip
python -m src.pipeline package-validate --package dist\knowledge-runtime-next.zip
python -m src.pipeline package-probe --package dist\knowledge-runtime-next.zip
```

升级顺序：

1. 保存当前 `/admin/active-db`、`/knowledge/documents`、发布记录和上一版包校验值。
2. 停止接收问答流量，并按部署方式停止 API 进程；不要在运行中的进程旁覆盖共享资产。
3. 在与 API 完全相同的 `DATA_DIR` 导入新包：

   ```powershell
   python -m src.pipeline package-import --package dist\knowledge-runtime-next.zip --data-dir $env:DATA_DIR --replace
   ```

4. 重启 API，依次核对 `/health`、`/ready`、`/admin/active-db` 和 `/knowledge/documents`。返回的包标识、数据版本、数据库路径、文档数和 chunk 数必须与 `package-validate` 结果一致，再恢复流量。

回退使用同一条受测路径：停止 API，重新校验上一版完整知识包，以 `--replace` 导入同一 `DATA_DIR`，重启并执行相同断言。导入函数只在单次命令内部临时保存被替换目标，用于异常时恢复事务；命令成功后该临时副本即删除，不能代替上一版包保留或持久卷备份。

运行知识包默认不含原始 PDF、后台任务、审计记录、人工修正源记录和全部质量历史。整包回退只恢复包内数据库、根 manifest、活动指针、结构化表、解析图片与来源策略；主机损坏或误删 `DATA_DIR` 时仍需从独立持久卷备份恢复其他运行证据。

### 6.2 完整运行数据备份与灾难恢复

完整备份使用独立的运行数据快照，不把知识包当作主机级备份。进入维护窗口、停止 API 并确认没有排队或运行任务后执行：

```powershell
python -m src.pipeline backup-create --data-dir $env:DATA_DIR --output D:\backups\structural-kb-latest.zip --actor operator --maintenance-window
python -m src.pipeline backup-validate --backup D:\backups\structural-kb-latest.zip
```

快照覆盖 `DATA_DIR` 下的原始 PDF、数据库、任务、审计、修正和质量历史；输出必须位于数据根之外。ZIP 未加密且可能包含受版权约束资料和用户操作证据，应存入具有静态加密、最小权限、版本控制和异地副本的受控介质，不进入 Git 或普通发布物。

灾难恢复时先在隔离位置校验快照，停止目标 API，再恢复到空目录；替换非空目录必须增加 `--replace`：

```powershell
python -m src.pipeline backup-restore --backup D:\backups\structural-kb-latest.zip --data-dir $env:DATA_DIR --replace --actor operator --maintenance-window
python -m src.app.core.config
```

恢复成功后启动 API，依次核对 `/health`、`/ready`、`/admin/active-db`、`/admin/quality/status` 和任务启动对账。恢复命令先完整校验和解压，再原子替换目标；失败会搬回原目录。若回退也失败，错误会给出保留旧数据的临时目录，禁止在保全该目录前重试或清理。格式和安全边界见[运行数据快照格式规范](../reference/运行数据快照格式规范.md)。

## 7. 构建、发布与回退

1. 执行 Dry Run，确认源文件和解析后端。
2. 重建知识库。管理端会在 `data/db_versions/{job_id}/` 隔离构建数据库、解析文本和图片，候选运行时、100 条常规检索与 12 条结构化检索门禁通过后才切换活动指针；失败候选保留供诊断，旧活动版本不变。
3. 完成人工校对后再次重建，并按 [质量运营流程](知识库维护与质量运营.md) 运行回答级盲测和完整发布质量门禁。候选激活门禁不包含外部 LLM 回答质量；运行知识包导出仍会复核完整门禁并阻断失败或过期证据。
4. 执行 [发布检查单](../releases/发布检查单.md)。
5. 保留当前和上一版完整运行知识包、包校验值与目标环境探针记录；按 6.2 节创建并离线校验完整运行数据快照。发布回归按 6.1 节整包重部署回退，主机级故障使用完整快照恢复。

## 8. 常见故障初查

| 现象 | 首先检查 |
| --- | --- |
| API 启动前报“配置校验失败” | 按错误中列出的变量修正 `.env`；运行 `python -m src.app.core.config` 复检，不要绕过校验 |
| 控制台空白或 404 | `frontend/dist` 是否存在；`STATIC_DIR` 是否指向该目录 |
| 控制台显示“后端暂时不可用” | 先请求 `/health`，再检查反向代理是否转发 `/admin/*`；该状态不是 API Key 错误 |
| 控制台请求 API Key | 浏览器对 `/admin/status` 的实际响应是否为 401；核对 `API_AUTH_ENABLED`、`API_KEYS` 和代理是否连到预期 API 实例 |
| Open WebUI 未启动 | `docker compose ps --all` 查看 `openwebui-preflight`；其非零退出说明 Key 关系、目标鉴权状态、API 连通性或模型发现失败，先修复探针错误，不要绕过依赖 |
| Open WebUI 无模型或返回 401 | 确认 `ENABLE_PERSISTENT_CONFIG=false`、基址为 `http://api:8000/v1`、`OPENWEBUI_API_KEY` 属于 `API_KEYS`；重新运行 preflight 并强制重建三个服务 |
| `401` | 是否开启 API 鉴权；请求是否传递 `Authorization: Bearer <key>` 或 `X-API-Key` |
| `/ready` 返回 503 | 查看响应中的 `reasons` 和 `checks`；核对 manifest、Chroma、集合数量、Embedding/MiMo 密钥与 BM25 初始化状态 |
| 日志难以关联请求和任务 | 记录响应 `X-Request-ID`，在 JSON 日志和任务 JSONL 中按 `request_id` 查询 |
| API 重启后任务显示“已中断” | 这是启动对账的预期结果；根据 `recovery.previous_status` 和任务日志核对候选产物，确认没有未收口副作用后重新提交，不手工改状态 |
| 任务显示“疑似卡滞” | 先比较 `progress_age_seconds` 与 `heartbeat_age_seconds`：心跳正常时检查当前长步骤和外部依赖；心跳过期时检查 API 进程。标记本身不会强制终止线程 |
| 任务记录显示 `JOB_RECORD_INVALID` | 备份 `data/jobs`，检查对应 JSON 是否截断、文件名与 `job_id` 是否一致；不要直接删除审计证据。修复或隔离前先确认没有关联运行任务 |
| 图片不显示 | `active_db.json` 的 `images_dir`、兼容回退的 `IMG_DIR`、`IMG_BASE_URL`、`PUBLIC_ASSET_BASE_URL`、原始 PDF 数据目录和反向代理路径 |
| 重建任务停在候选门禁 | 打开该任务日志和 `data/db_versions/{job_id}/quality/candidate_activation_gate.md`；按失败检查修正，不要手工改活动指针绕过门禁 |
| 知识包导入或探针失败 | 先运行 `package-validate`；检查 Python/Chroma/架构、包来源、同名资产、磁盘空间及完整错误输出；不得绕过 `package-probe` 强制激活 |
| 完整快照创建或恢复失败 | 确认 API 已停止、没有活动/损坏任务、ZIP 位于 `DATA_DIR` 外且磁盘空间充足；先运行 `backup-validate`。若错误给出保留旧数据的临时目录，先保全该目录，不要再次覆盖 |
| 回答无依据或检索异常 | 活动数据库、manifest 版本、评估报告是否过期；不要直接把模型回答当作诊断证据 |

发生影响用户、内容权利或数据安全的故障时，暂停受影响入口、保全日志和版本信息，并按 Runbook 模板创建事件记录。
