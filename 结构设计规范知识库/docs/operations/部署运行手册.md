## 1. 适用范围

本文档覆盖宿主机和 Docker Compose 运行方式。Dockerfile 使用多阶段构建生成并复制 `frontend/dist`；GitHub Actions 已在 Linux Runner 完成镜像构建、API 容器健康检查和静态控制台检查。当前工作环境的 Docker engine 未运行，因此 API 与 Open WebUI 的完整 Compose 拓扑仍缺少本机联调证据。

## 2. 前置条件

- Python 3.11 运行环境。
- Node.js 22 与 npm 10.9.8，用于可复现地构建 Vue 控制台。版本契约同时记录在 `frontend/package.json`，`frontend/.npmrc` 会拒绝不匹配的 npm 版本；不得用 npm 11 重写锁文件。
- 使用容器方式时需要 Docker Engine 与 Docker Compose v2。
- 以下两种数据准备方式任选其一：在构建环境持有 PDF、MinerU（或显式选择 PyMuPDF）和 Embedding 能力并完成重建；或在轻量运行环境导入已验证的运行知识包。导入运行包不需要 MinerU。
- `ZHIPUAI_API_KEY` 和 `MIMO_API_KEY`。不将真实密钥提交到 Git。

## 3. 本地启动

```powershell
Copy-Item .env.example .env
# 在 .env 中填写 ZHIPUAI_API_KEY、MIMO_API_KEY 和生产所需的 API_KEYS。

python -m pip install --require-hashes -r requirements-runtime.txt
Push-Location frontend
npm install --global npm@10.9.8
npm ci
npm run build
Pop-Location

python -m src.app.core.config
python -m uvicorn src.app.main:app --host 127.0.0.1 --port 8000
```

只有需要从 PDF 重新解析和构建知识库的环境才安装 `requirements.txt`。API、控制台和已验证运行知识包的部署使用精确锁定的 `requirements-runtime.txt`；自动化测试使用 `requirements-dev.txt`。

运行锁和开发锁同时固定版本与分发包哈希。直接依赖只在 `.in` 文件维护，`dependency-lock.json` 固定 Python 版本、`uv` 版本和 `exclude_newer` 时间截点。升级时先更新直接依赖和时间截点，再用固定工具执行：

```powershell
python -m pip install -r requirements-tools.txt
python scripts\lock_dependencies.py --write
python scripts\lock_dependencies.py --check
```

禁止手工修补 `.txt` 锁文件，也禁止在生产安装中去掉 `--require-hashes`。CI 会在 Ubuntu/Windows 分别安装开发锁并运行全量测试；Docker 构建另行验证 Linux 运行锁。

校验：

```powershell
Invoke-WebRequest http://127.0.0.1:8000/health
Invoke-WebRequest http://127.0.0.1:8000/ready
```

根路径会重定向到 `/static/index.html`。若未构建 `frontend/dist`，控制台不会被挂载。

## 4. Docker Compose 启动

Docker 镜像会在独立 Node 22 构建阶段固定 npm 10.9.8，再执行 `npm ci` 和生产构建；CI 使用相同组合。最终镜像只复制 `frontend/dist`，不携带 Node.js 工具链。运行时镜像还包含评估集、规范元数据和动态 PDF 页面渲染所需的 PyMuPDF。

Compose 文件显式使用项目名 `structural-spec-kb`，避免中文目录名无法自动转换为合法 Compose 项目名。
服务级 `.env` 声明为可选，因此 CI 和代码审查环境可以在没有私密配置文件时执行 `docker compose config -q`；真正启动可用服务前仍必须从示例创建 `.env`，并通过配置预检和 `/ready` 检查。

```powershell
Copy-Item .env.example .env
# 填写模型密钥；启用鉴权时同时配置 API_KEYS、OPENWEBUI_API_KEY 和 ASSET_SIGNING_KEY。
python -m src.app.core.config
docker compose config -q
docker compose up --build -d
docker compose ps
Invoke-WebRequest http://127.0.0.1:8000/health
Invoke-WebRequest http://127.0.0.1:8000/static/index.html
```

Compose 将整个 `./data` 挂载到 `/app/data`，将 `./db` 和 `./logs` 分别持久化，并用命名卷保存 Open WebUI 内部状态。这样可覆盖 manifest、活动数据库指针、数据库版本、来源策略、结构化表、校对记录和评估证据。该挂载也会把 `data/raw` 提供给 API 进程；页面是否允许展示由 `data/metadata/specs.json` 控制，但来源策略不替代内容授权审核。

Open WebUI 使用 `http://api:8000/v1` 作为 OpenAI-compatible 基址。若 `API_AUTH_ENABLED=true`，`OPENWEBUI_API_KEY` 必须等于 `API_KEYS` 中的一个有效 Key；Open WebUI 已经初始化过连接时，环境变量变化可能需要在其管理界面同步更新。

## 5. 生产配置最低要求

- 设置 `API_AUTH_ENABLED=true` 和强随机 `API_KEYS`。
- 为 Open WebUI 设置单独的 `OPENWEBUI_API_KEY`，并将同一值加入 `API_KEYS`。
- 设置独立、随机且至少 32 字符的 `ASSET_SIGNING_KEY`；按客户端阅读时间设置 `ASSET_URL_TTL_SECONDS`，默认 3600 秒。
- 将 `CORS_ORIGINS` 限制为明确的控制台域名。
- 将 `PUBLIC_ASSET_BASE_URL` 配置为同一个 FastAPI 服务的外部资源前缀；受保护签名必须由该服务验证，不能把资源路径改指向无策略的静态主机。
- 在 `data/metadata/specs.json` 为每份来源显式设置 `image_access` 和 `page_image_access`。网上收集的扫描件默认使用 `authenticated`，未确认展示许可的来源使用 `disabled`；只有确认可公开的资料使用 `public`。
- 通过反向代理终止 TLS；不要把开发端口直接暴露到公网。
- 生产运行必须使用独立的 `DB_DIR`、`IMG_DIR`、日志和备份目录。
- 使用 `LOG_FORMAT=json` 输出可采集的单行结构化日志，并在日志平台按 `request_id`、`event`、`job_id`、`status` 和 `error_code` 建立索引。
- 检查模型供应商的地区、数据保留和密钥管理约束。

### 5.1 运行观测与告警

API 为每个请求生成或规范化 `X-Request-ID`，在响应、结构化日志和由该请求创建的后台任务日志中保持一致。生产日志应写入标准输出并由容器平台或日志代理采集，不依赖本地临时日志文件作为唯一证据。

最小告警建议：

1. `/health` 连续失败：进程或网络故障，立即告警。
2. `/ready` 连续返回 503：按 `reasons` 区分知识库、密钥、BM25、manifest 或集合数量问题；停止接收问答流量，但保留控制台用于诊断。
3. `/metrics` 中 5xx 状态持续增长、`errors_by_code` 异常增加或请求最大/平均耗时显著抬升：保留关联 `request_id` 并检查对应事件日志。
4. 后台任务长时间处于 `running` 或出现 `job_failed`：通过 `/admin/jobs/{job_id}/logs` 核对步骤和创建请求。

`/metrics` 是单进程、重启清零的运行快照。多 worker 或多副本部署不能直接累加这些值，应由外部采集系统按实例保存和聚合。日志禁止写入 API Key、完整用户问题、完整模型回答、受限规范原文和客户端 IP；当前 RAG 事件只记录查询字符数、候选数量和上下文规模。

## 6. 运行知识包部署

知识资产维护者在已完成校对和质量验证的构建环境导出：

```powershell
python scripts/verify_quality.py

# 默认不包含原始 PDF
python -m src.pipeline package-export --output dist\knowledge-runtime.zip

# 只在来源权利和目标用途允许时显式包含原始 PDF
python -m src.pipeline package-export --output dist\knowledge-runtime-with-pdf.zip --include-source-pdfs
```

导出会实时复核当前数据版本、评估集哈希和报告年龄，默认有效期为 168 小时。门禁失败时不会生成知识包，并在 `data/audit/package_exports/` 留下阻断记录。仅在已有独立风险批准的受控例外中使用：

```powershell
python -m src.pipeline package-export `
  --output dist\knowledge-runtime.zip `
  --quality-waiver-actor "release-owner" `
  --quality-waiver-reason "受控排障交付，禁止对外发布"
```

责任人和原因会进入 v2 及以上版本的包清单与审计记录。不得用豁免代替重新评估或内容授权判断。

目标环境应先做只读校验，再导入默认 `data/` 目录：

```powershell
python -m src.pipeline package-validate --package dist\knowledge-runtime.zip
python -m src.pipeline package-probe --package dist\knowledge-runtime.zip
python -m src.pipeline package-import --package dist\knowledge-runtime.zip
python -m uvicorn src.app.main:app --host 127.0.0.1 --port 8000
```

`package-validate` 只做静态格式、哈希和兼容性检查。`package-probe` 会在临时目录隔离导入，并由子进程真实打开 Chroma、核对集合数量和样本可读性；它不改变当前项目数据。只有两项都通过后才执行正式导入。

正式导入会把数据库安装为 `data/db_versions/import-<package_id>/`，复制包内结构化表、图片和来源策略，并在最后更新 `data/active_db.json` 与 `data/manifest.json`。活动指针使用项目相对路径，允许同一 `data/` 在 Windows、Linux 和容器之间迁移；读取端仍兼容旧版 Windows 绝对路径。API 已运行时必须在导入后重启；当前命令不会热重载正在运行的进程。

操作约束：

1. 同一版本已安装或同名资产内容不同时，导入默认失败，不覆盖现有数据。
2. `--replace` 会覆盖冲突目标，只能在备份和确认包来源后使用。
3. `--no-activate` 只安装和检查，不切换活动数据库。
4. `--data-dir` 主要用于预安装、测试或项目数据目录迁移；当前 API 默认读取仓库 `data/active_db.json`，自定义目录不会自动改变在线进程的数据根。
5. 原始 PDF 默认不在包内；此时动态 `/page-images/*` 不可用，但已有解析图片仍可引用，纯文本问答不受影响。
6. 校验通过证明包未损坏，不证明内容获得传播、展示或商业使用授权。
7. 当前受控兼容矩阵仅覆盖 CPython 3.11、Chroma 1.5.9、x86_64 Windows/Linux；矩阵外环境必须重新验证，不得跳过探针。

## 7. 构建、发布与回退

1. 执行 Dry Run，确认源文件和解析后端。
2. 重建知识库。管理端会在 `data/db_versions/{job_id}/` 隔离构建数据库、解析文本和图片，候选运行时、100 条常规检索与 12 条结构化检索门禁通过后才切换活动指针；失败候选保留供诊断，旧活动版本不变。
3. 完成人工校对后再次重建，并按 [质量运营流程](知识库维护与质量运营.md) 运行回答级盲测和完整发布质量门禁。候选激活门禁不包含外部 LLM 回答质量；运行知识包导出仍会复核完整门禁并阻断失败或过期证据。
4. 执行 [发布检查单](../releases/发布检查单.md)。
5. 保留当前 manifest、结构化表版本、活动数据库、原始 PDF 和图片资产备份；失败时先恢复这些版本与资产，再恢复服务。

## 8. 常见故障初查

| 现象 | 首先检查 |
| --- | --- |
| API 启动前报“配置校验失败” | 按错误中列出的变量修正 `.env`；运行 `python -m src.app.core.config` 复检，不要绕过校验 |
| 控制台空白或 404 | `frontend/dist` 是否存在；`STATIC_DIR` 是否指向该目录 |
| Open WebUI 无模型或返回 401 | 基址是否为 `http://api:8000/v1`；`OPENWEBUI_API_KEY` 是否属于 `API_KEYS`；既有 Open WebUI 持久化连接是否仍保存旧配置 |
| `401` | 是否开启 API 鉴权；请求是否传递 `Authorization: Bearer <key>` 或 `X-API-Key` |
| `/ready` 返回 503 | 查看响应中的 `reasons` 和 `checks`；核对 manifest、Chroma、集合数量、Embedding/MiMo 密钥与 BM25 初始化状态 |
| 日志难以关联请求和任务 | 记录响应 `X-Request-ID`，在 JSON 日志和任务 JSONL 中按 `request_id` 查询 |
| 图片不显示 | `active_db.json` 的 `images_dir`、兼容回退的 `IMG_DIR`、`IMG_BASE_URL`、`PUBLIC_ASSET_BASE_URL`、原始 PDF 数据目录和反向代理路径 |
| 重建任务停在候选门禁 | 打开该任务日志和 `data/db_versions/{job_id}/quality/candidate_activation_gate.md`；按失败检查修正，不要手工改活动指针绕过门禁 |
| 知识包导入或探针失败 | 先运行 `package-validate`；检查 Python/Chroma/架构、包来源、同名资产、磁盘空间及完整错误输出；不得绕过 `package-probe` 强制激活 |
| 回答无依据或检索异常 | 活动数据库、manifest 版本、评估报告是否过期；不要直接把模型回答当作诊断证据 |

发生影响用户、内容权利或数据安全的故障时，暂停受影响入口、保全日志和版本信息，并按 Runbook 模板创建事件记录。
